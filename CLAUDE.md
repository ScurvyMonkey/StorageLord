# CLAUDE.md — Storage Lord

## Project Overview

**Storage Lord** is a Unity 6 satisfying, grid-based space logistics micro-game. The player manages one storage platform for an indifferent Company: goods arrive at Receiving, get routed via conveyors into grid-anchored containers, and get routed back out to Shipping to fulfill the Company's orders before their deadlines. Full design context lives in `docs/GDD.md` — **read it before scoping any new system**, especially its Open Questions section, since several core mechanics (grid cell size, container type-matching, conveyor complexity) aren't nailed down yet (camera style was resolved by #2 — free-orbit perspective).

Built with C# and Universal Render Pipeline (URP), 3D. Uses the **SpacePlatformKit** (modular station geometry) and **ScifiCommoditiesTradeGoodsLootCollection** (goods/cargo meshes) asset packs — both are static meshes/prefabs only; there is no gameplay logic to inherit from them.

**Repo:** `ScurvyMonkey/StorageLord` (GitHub — hosts both code and the Issues backlog)

## Current Phase: Phase 1 — Core Loop

Nothing is implemented yet — this is a from-scratch start. Phase 1 is the MVP: a working Receive → Store → Ship loop on a single platform, with clean grid placement as a first-class requirement (not a later polish pass). Phase 2 (goods categories/type-matching, conveyor junctions/splitters, order complexity, audio/VFX polish) is explicitly out of scope until Phase 1's loop is playable end-to-end. See [Roadmap](docs/GDD.md#roadmap) in the GDD for the full phase breakdown.

**Phase 1 sub-system sequencing** (update this list as each sub-system is picked up/completed):
- **Grid & placement system** — first pass landed: `GridConfig` (cell size + rotation snap, `Assets/Data/GridConfig.asset`), `GridVisualizer` (Scene view grid gizmo), and the `Platform Grid Placer` Editor window (see Platform Assembly below) all exist. A runtime `GridManager` (`Assets/Scripts/Grid/GridManager.cs`) now exists too, landed as part of #4 once `ConveyorManager` needed to share occupancy state with `PlacementManager` — exactly the trigger this file previously named as the reason to build it. **Not yet done:** `cellSize` (4m) is an unverified placeholder — check it against SpacePlatformKit piece footprints via the grid gizmo and adjust; occupancy tracking is one-cell-per-piece-origin, not real per-piece footprint checking, so larger pieces can still visually overlap a neighbor.
- **Platform assembly from SpacePlatformKit pieces** — first pass landed, resolved as an **Editor-time, hand-authored** workflow (not player-placed at runtime): `Assets/Scripts/Grid/Editor/PlatformGridPlacerWindow.cs` (**Window → Storage Lord → Platform Grid Placer**) lets you pick a prefab and click-place it in the Scene view, snapped to the grid, parented under a `Platform` root. This is a level-design tool for you, not a system players interact with — kept clearly separate from the future runtime `PlacementManager` (containers/conveyors), though both will share `GridConfig`.
  - **Scaled up to a ~64x64m (16x16 cell) platform (#11)**, replacing the original ~24x32m layout — an 8-column x 4-row grid of `SpacePlatformLargeBlue` (32 pieces, same piece/spacing pattern the original small layout already used: 8m column spacing, 16m row spacing, matching the kit's own built-in joint overlap). `Receiving`/`Shipping` moved to opposite ends (`ConnectionPoint` cells `(0,0,6)`/`(0,0,-6)`, ~48m/12 cells apart along Z, both near X=0) — their hand-off cells end up 11 cells apart (`ConveyorManager.MaxDragSegments` is 10), so connecting them genuinely requires at least two chained drags, not a cosmetic distance. Built by writing a one-off Editor script that calls the same `PrefabUtility.InstantiatePrefab` + `GridConfig`-cell-spacing approach `PlatformGridPlacerWindow` itself uses (not driven through the tool's own Scene View GUI, which isn't reachable via automation) — same mechanism, same result, no new runtime code. Each dock's new root position was derived by preserving its existing world-space root-to-`ConnectionPoint` offset (rotation unchanged) rather than guessed, so the compound prefab's internal joint alignment is untouched. `CameraConfig.panBoundsRadius` (40→60) and `zoomMax` (60→100) were also increased — the platform's own corners (~45m from center) sat outside the old 40m pan radius, which would have made parts of the new platform physically unreachable by camera pan; caught during `/arch`, not found live. Live-verified end-to-end: connected Receiving to Shipping across the full 11-cell gap via two chained drags (simulated input), confirmed goods actually traveled the whole distance and were credited to an active order, console clean.
- **Conveyor movement** — first pass landed (#4), extended by #6 (Receiving), #5 (container handoff — see Storage System), and #7 (networks: junction merging, backflow prevention, multi-level stacking): `ConveyorManager` (runtime, `Assets/Scripts/Conveyors/`) is the platform's second placer, alongside `PlacementManager`. Players toggle conveyor placement mode (C), left-click-drag from a start cell to lay a straight run of up to 10 segments (clamped to whichever axis the drag moved further along), cycle flow direction with Q/R while dragging, PageUp/PageDown to select the height level the run will be placed at, and release to confirm. A run overlapping an already-occupied cell is rejected — *except* its own last cell may land on an existing conveyor segment, merging into it as a junction (that segment keeps its own flow direction rather than being replaced) — and a run whose flow, simulated forward through whatever it merges into, would ever reach the Receiving dock's output cell is rejected outright as backflow. Right-click removes a single segment (no cascade — segments aren't stacked) and destroys any `GoodsAgent` currently riding that cell along with it. Segments (and goods riding them) hover `ConveyorData.hoverHeight` above the deck surface via `SegmentWorldPosition(cell)`, now supporting arbitrary height levels (`Vector3Int.y`, sharing `GridManager`'s occupancy the same way container stacking does) rather than deck-only — unlike containers' auto-derived stacking, conveyor height is player-chosen, since the point here is deliberately routing at a chosen alternate level (e.g. over an obstacle), not piling. Introduces the project's first goods concept: `GoodsData`/`GoodsAgent` (`Assets/Scripts/Goods/`) — a real object with position state, not a shader trick. `ConveyorManager.RegisterGoodsAgent(GoodsAgent)` (public, added in #6) is the one entry point for handing an externally-spawned good into per-frame movement tracking — both the Editor-only debug spawn (G, aimed at a placed segment — a legacy manual-testing convenience now that `ReceivingManager` is the real source) and `ReceivingManager` route through it, so there's one shared movement list, not two. `ConveyorManager` advances any registered `GoodsAgent` sitting on a segment toward the next cell each frame; at a junction cell (2+ upstream feeders), the main line (traced forward from the Receiving dock's output cell) gets priority, except when it also won that cell's last contention, in which case a different feeder is favored — fair alternation so a busy main line can't starve a side line forever. Uses `ConveyorData` (prefab, `beltSpeed`, `hoverHeight`) and `GoodsData` (display name + prefab), both following `ContainerData`'s minimal pattern. **Not yet done:** real conveyor/goods art (`TurretPlatformFlyingBlue`/`Pallet1` placeholders), splitting (1-to-N output distribution — still Phase 2), and any piece that moves goods between height levels (stacked levels are independent parallel networks for now).
- **Containers/storage (placement)** — first pass landed (#1), placement rules reworked to support-required auto-stacking (#3): `PlacementManager` (runtime, `Assets/Scripts/Placement/`) is the game's first real manager, created by the new `Bootstrapper` (`Assets/Scripts/Core/`). Players toggle placement mode (Tab), aim with the mouse to snap a ghost preview to the grid — height is no longer a manual input; the piece always snaps onto the deck or directly atop whatever's already placed in that X/Z column, so a second piece placed at the same column auto-stacks one level higher — rotate with R, confirm with left-click, remove with right-click (removing a piece also removes everything stacked directly above it in that column). Uses `ContainerData` (minimal — display name + prefab only; capacity/type-filtering is still Phase 2) and a placeholder container visual (`ContainerData_CargoBoxPlaceholder.asset`, since no real container art exists yet). Mutually exclusive with `ConveyorManager`'s placement mode as of #4 — entering one force-exits the other, so `R` is never ambiguous between "rotate the container ghost" and "cycle belt flow direction." **Not yet done:** real container art/design, actual goods storage/capacity (that's `StorageManager`, a separate not-yet-started piece), any stack-height cap (unlimited for now), and verifying a deck-level (height 0) placement actually lands on real platform geometry rather than open space past its edge (`PlacementManager` has no concept of platform footprint/bounds yet).
- **Camera** — first pass landed (#2): `CameraManager` (runtime, `Assets/Scripts/Camera/`) drives the scene's pre-placed `MainCamera`-tagged `Camera` as a free-orbit rig (Shapez 2-style, resolving the GDD's camera Open Question) — hold middle-mouse and drag to orbit/tilt, WASD/arrows to pan, scroll to zoom. Uses `CameraConfig` (`Assets/Data/CameraConfig.asset`) for all tuning. Also fixed a pre-existing gap while wiring this in: `Bootstrapper` had never actually been added to `SampleScene` — nothing in the scene created it, so `PlacementManager` never ran either. Added a `Bootstrapper` GameObject to the scene with all its references wired (`GridConfig`, `PlacementEventChannel`, `ContainerData_CargoBoxPlaceholder`, `CameraConfig`, the new `CameraRig`).
- **Receiving dock + goods spawn scheduling** — first pass landed (#6): `ReceivingManager` (runtime, `Assets/Scripts/Docks/`) spawns goods automatically — the platform's first real goods source, replacing the need for `ConveyorManager`'s debug spawn for normal testing. `ReceivingDock` is deliberately **fixed/Editor-placed, not runtime-placeable** (resolved via `/ba` for #6 against the GDD's own "fixed dock" language). Spawns at a fixed rate (`ReceivingData.itemsPerMinute`, default 30 = one every 2s) — but only once a real conveyor segment is actually placed at the output cell (`ConveyorManager.HasSegmentAt`, post-#6 fix — previously spawned unconditionally, since `GoodsRestPosition` is a pure coordinate computation that doesn't care whether a segment GameObject exists there, so goods would visibly hover in open space with nothing under them until a belt eventually got built); if the dock's last-spawned good is still sitting unmoved on the output cell, that spawn is skipped rather than stacking. The output cell is `ConnectionPoint`'s own cell — `ReceivingManager` deliberately does NOT register it with `GridManager` (post-#9 fix, direct user report), so a belt can be placed flush against the dock instead of one cell short of it, bridged only by an easy-to-miss energy-connector light that a player naturally tried and failed to fill with a real piece. Ramping the spawn rate over a session (GDD's open question) stays deliberately unresolved — flat rate only. **Not yet done:** player-placeable Receiving docks (explicitly deferred to its own future `/ba` pass, not forgotten), multiple docks with independent rates.
- **Player-selectable Receiving goods (#15)** — the dock no longer always spawns `ReceivingData.goodsData` fixed for the whole session: left-clicking a registered `ReceivingDock`'s own geometry (outside both `PlacementManager`/`ConveyorManager` placement modes, where left-click already means something else) cycles `ReceivingManager`'s current selection forward through `_goodsChoices`, a list built once in `Initialize()` from every distinct `GoodsData` referenced by `ShippingScheduleData.scheduledOrders` plus `WaveEscalationData.goodsPool` (deduplicated) — a deliberately content-derived list, not a separate authored/unlock list, so it grows automatically as more order content gets authored with zero progression/gating system (a conscious Phase-1-compatible reinterpretation of a "grows over time" ask that would otherwise have reached into unscoped meta-progression backlog — resolved via `/ba`). Falls back to `ReceivingData.goodsData` directly if the derived list ends up empty; starts the selection on `goodsData` if it appears in the derived list, otherwise the list's first entry. `ReceivingHUD` (bare `OnGUI`, bottom-left corner) shows the current selection. Existing fulfillment priority (oldest-activated order serviced first when several want the same type) is unrelated, already-shipped `ShippingManager` behavior — this issue never touched it.
- **Compound dock visuals + connection-point marker** (post-#9 polish, direct request): both docks were upgraded from a single placeholder `Building` piece to hand-built compound prefabs (`Assets/Prefabs/Shipping.prefab` — user-authored; `Assets/Prefabs/Receiving.prefab` — mirrors it, Blue kit instead of Green for contrast) — 4 rotated `BuildingMedium*` pieces plus a `Hangar*` piece with an embedded `TurretPlatformFlying*` as the visual belt-connection stub. Because that connector sits at a hand-placed offset inside the compound, not a clean one-cell offset from the prefab root, `ReceivingDock`/`ShippingDock` each gained a serialized `connectionPoint` Transform (`ConnectionPoint` property, falls back to `transform` if unassigned) — `ReceivingManager`/`ShippingManager` now derive the dock's own registered cell from `ConnectionPoint.position`, not the root's, so the belt hand-off cell (still one cell further in `GetOutputDirection()`/`GetInputDirection()`) lines up with wherever the connector actually is, regardless of how the compound is internally arranged. Root placement Y matters a lot here: `BuildingMedium*` pieces rest correctly at world Y≈0 standalone, but `Hangar*` (used standalone as a storage container, #5) rests correctly at `deckSurfaceHeight` (≈0.69) — a single compound root Y can't satisfy both conventions at once, so the connector/Hangar side is prioritized (root Y chosen so the connector lands at `deckSurfaceHeight`, matching every other deck-level fixture) since that's the side gameplay actually touches; the buildings end up close to the same height anyway since `deckSurfaceHeight` is the more fundamentally correct "resting on the deck" reference than the `Y=0` the original single-piece docks happened to use. Root X/Z is chosen so the connector lands exactly on its grid cell's center (verify via `GridConfig.WorldToCell3D`/`Cell3DToWorld` round-trip), not guessed. **Not yet done:** the compound's much larger footprint (~8.65m × 8.01m, roughly 2×2 cells) is still only registered as a single cell with `GridManager` — the same known, pre-existing "occupancy is one-cell-per-piece-origin" gap this file already documents under Grid & Placement System, now more visually apparent than it was for the old single-piece docks.
- **Shipping dock + Company orders/deadlines** — first pass landed (#9): `ShippingManager` (runtime, `Assets/Scripts/Docks/`) runs a data-driven schedule of `OrderData` assets (`ShippingScheduleData`), activating each independently once its own `startDelaySeconds` elapses — multiple orders can be active at once, each on its own `deadlineSeconds` countdown from its own activation. `ShippingDock` is a fixed, Editor-placed component mirroring `ReceivingDock` exactly. Fulfillment works two ways: a `GoodsAgent` arriving directly at a dock's input cell via conveyor (`ShippingManager.TryFulfillAt`, called from `ConveyorManager.AdvanceGoods`'s hand-off chain alongside the existing container hand-off), or automatic withdrawal from `StorageManager`'s containers each frame (`ContainerInstance`/`StorageManager` gained a `TryWithdraw`, the first time containers have ever released goods rather than only accepted them — draining a container to zero fully unlocks it for a different type next). When multiple active orders want the same type, the oldest-activated one is credited first. A missed deadline just marks the order expired and removes it — `OrderEventChannel` (new, mirrors `PlacementEventChannel`'s pattern) raises `OnOrderActivated`/`OnOrderFulfilled`/`OnOrderMissed`, intended for a future `ScoreManager` to subscribe to. A minimal `ShippingHUD` (OnGUI, no styling) lists active orders' progress — a real styled HUD is Phase 2 UI polish. **Not yet done:** multi-good orders (Phase 2), real scoring/consequences, any styled UI, player-placeable/multiple Shipping docks.
- Basic scoring (orders fulfilled/missed) — not yet started (the event channel above is ready for it)

If a spec or a piece of work seems to require a later-phase system (goods categories, junctions/splitters, multi-platform, meta-progression), stop and flag it rather than building a placeholder for it.

## Proposed Manager Hierarchy (Phase 1)

`Bootstrapper`, `PlacementManager`, `CameraManager`, `GridManager`, `ConveyorManager`, `ReceivingManager`, `StorageManager`, `ShippingManager`, `GameManager`, `WeightManager`, `ScoreManager`, `UpgradeManager`, `SoundManager`, and `AmbienceManager` are real (#1, #2, #4, #5, #6, #9, #12, #14, #25, #27, #29) — everything else below is still a **starting proposal**, not settled fact. Update each entry the moment real implementation diverges from it.

All managers are singletons created by `Bootstrapper.cs` via `DontDestroyOnLoad`. **Do not create singletons outside this pattern.** `Bootstrapper` itself is deliberately minimal — it only creates what its own issues needed (`GridManager`, `PlacementManager`, `CameraManager`, `ConveyorManager`, `ReceivingManager`, `StorageManager`, `WeightManager`, `ShippingManager`, `GameManager`); each other manager below gets added to it only once a real issue builds it, not preemptively. `ShippingHUD`/`GameOverHUD`/`WeightHUD` also get created here despite not being real managers (passive displays with nothing to inject beyond finding their one manager each) — kept in one place so every runtime object comes from Bootstrapper rather than some being hand-placed in the scene.

```
Bootstrapper (exists)
├── GameManager        — (exists, #12) Owns the run's only loss condition so far: counts OrderEventChannel.OnOrderMissed, and at GameRulesData.maxMissedOrders (default 10) halts PlacementManager/ConveyorManager/ReceivingManager/ShippingManager via each one's own SetGameActive(false) — no win condition, restart flow, or scoring beyond the raw miss count yet. Created via code by Bootstrapper, deliberately LAST among the managers in Awake() — it needs all four to already exist so it has something to halt. Its OrderEventChannel subscription happens inside Initialize() itself, not OnEnable() alone (same Camera.main-precedent pitfall as every other Bootstrapper-created manager: OnEnable() fires before Initialize() sets real references)
├── GridManager         — (exists) Shared runtime occupancy registry (IsOccupied/Register/Unregister/NextFreeHeightLevel) — landed with #4 once ConveyorManager needed to share cell-occupancy state with PlacementManager, the exact trigger this entry used to name. Created via code by Bootstrapper, before either placer
├── PlacementManager     — (exists) Ghost preview (support-required auto-stack height, derived from GridManager occupancy)/rotation (R) adjustment, confirm (left-click)/remove (right-click, cascades up the stack). Mutually exclusive with ConveyorManager's placement mode (#4) via reciprocal ExitPlacementMode() calls. Created via code by Bootstrapper (not a prefab) — its GridConfig/GridManager/PlacementEventChannel/ContainerData references are injected via Initialize(), not the Inspector; SetStorageManager (#14) wires a StorageManager reference afterward so container removal un-tracks properly (see Storage System)
├── CameraManager         — (exists) Free-orbit camera rig — middle-mouse drag orbits/tilts, WASD/arrows pan, scroll zooms (including during placement mode — placement no longer uses scroll). Drives the scene's pre-placed MainCamera (never destroys/recreates/reparents it — see Camera System below). Created via code by Bootstrapper — its CameraConfig/CameraRig references are injected via Initialize()
├── ConveyorManager       — (exists) Drag-based placement (C to toggle, Q/R cycle flow direction, PageUp/PageDown select height level) of conveyor runs — can merge into an existing segment as a junction, rejects placements that would route back to Receiving — sharing GridManager occupancy with PlacementManager; also drives per-frame GoodsAgent movement (RegisterGoodsAgent is the shared entry point) along placed segments, arbitrating junction traffic with main-line priority and fair alternation (#7). Mutually exclusive with PlacementManager's placement mode. Created via code by Bootstrapper — its GridConfig/GridManager/PlacementEventChannel/ConveyorData/debug GoodsData references are injected via Initialize(); SetStorageManager/SetReceivingManager wire the rest after all managers exist. GetSegmentCells()/RemoveCells(cells) (#14) let WeightManager surgically remove just the conveyor cells on a failed platform segment, without disturbing the rest of a longer run that continues onto healthy segments
├── ReceivingManager      — (exists) Finds every ReceivingDock at startup (registers each one's cell with GridManager), then spawns GoodsAgents onto each dock's output cell on a fixed timer (ReceivingData.itemsPerMinute), handing them to ConveyorManager.RegisterGoodsAgent. Lets the player cycle which goods type is currently spawned (#15) — left-click on a dock's geometry outside either placement mode advances CurrentGoods through a content-derived list built once from ShippingScheduleData/WaveEscalationData. Created via code by Bootstrapper, after ConveyorManager (needs a live reference) — its GridConfig/GridManager/ConveyorManager/ReceivingData/ShippingScheduleData/WaveEscalationData references are injected via Initialize(); SetPlacementManager (#15) wires a PlacementManager reference afterward so goods-selection clicks are ignored while container placement mode is active
├── StorageManager         — (exists) Registry of placed containers, keyed by cell — subscribes to PlacementEventChannel.OnPiecePlaced, registering only pieces carrying a ContainerInstance marker (that event also fires for conveyor segments). Exposes TryStoreAt(cell, goodsData)/TryWithdraw(goodsData) for ConveyorManager/ShippingManager, and GetContainerCells()/RemoveContainerAt(cell) (#14) for WeightManager and PlacementManager's own removal path. Reports every deliver/withdraw's weight delta to WeightManager. Created via code by Bootstrapper — its PlacementEventChannel reference is injected via Initialize(); SetWeightManager (#14) wires the rest after WeightManager exists
├── WeightManager          — (exists, #14) Tracks each platform floor segment's current stored-goods weight against its capacity (PlatformSegmentData.capacityKg) — notified by StorageManager after every deliver/withdraw, goods in transit on a conveyor never count. Crossing capacity destroys every container/stored good/conveyor cell physically on that segment (via StorageManager.RemoveContainerAt + ConveyorManager.RemoveCells) and resets its tracked weight to zero — the tile itself stays, only what was built on it is lost. Resolves which segment owns a cell by measuring each PlatformSegment instance's real Renderer bounds (X/Z only, height-agnostic) rather than assuming a footprint-in-cells formula. Created via code by Bootstrapper, right after StorageManager (needs both StorageManager and ConveyorManager, both already created by then) — its GridConfig/GridManager/StorageManager/ConveyorManager references are injected via Initialize()
├── ShippingManager          — (exists) Activates OrderData from ShippingScheduleData on independent per-order timers (multiple can be active at once), fulfills via direct dock arrival (TryFulfillAt, called by ConveyorManager) or automatic container withdrawal (StorageManager.TryWithdraw, checked every frame) — oldest-activated matching order is credited first either way. Raises OrderEventChannel events; no scoring logic itself. Created via code by Bootstrapper, after StorageManager — its GridConfig/GridManager/StorageManager/ShippingScheduleData/OrderEventChannel references are injected via Initialize()
├── ScoreManager              — (exists, #25) Tracks the player's running money total — subscribes to OrderEventChannel.OnOrderFulfilled and awards moneyReward for any non-Priority-tier order. TrySpend(int) (#27) is the one spend path every purchase goes through. Created via code by Bootstrapper — needs only the shared OrderEventChannel asset, so its creation order relative to other managers doesn't matter
├── UpgradeManager             — (exists, #27) Owns two global, retroactive upgrade tracks — conveyor belt speed and platform weight capacity — each a purchased-tier count against a fixed UpgradeData tier list (multiplier, costMoney). ConveyorManager/WeightManager read ConveyorSpeedMultiplier/PlatformCapacityMultiplier live wherever the underlying stat is used, so a purchase instantly affects every belt/segment already placed. Created via code by Bootstrapper, after ScoreManager (needs a live TrySpend reference) — ConveyorManager/WeightManager are wired a reference afterward via SetUpgradeManager(), the same late-wiring shape every other cross-manager reference in Bootstrapper already uses
├── SoundManager               — (exists, #29) General-purpose audio playback utility — one dedicated AudioSource per one-shot cue (placement confirm/reject, order fulfilled/missed), played via `.Play()` restart semantics rather than `PlayOneShot` (a multi-cell conveyor drag confirms via `OnPiecePlaced` once per cell, so `PlayOneShot` would stack overlapping instances into an audible stutter), plus a shared belt-hum loop and two alternating ambience sources for crossfading. Subscribes directly to `PlacementEventChannel.OnPiecePlaced`/`OrderEventChannel.OnOrderFulfilled`/`OnOrderMissed` — zero new call sites in `PlacementManager` or `ConveyorManager`'s confirm path. Created via code by Bootstrapper — only needs Bootstrapper-level asset references, so creation order relative to other managers doesn't matter
├── AmbienceManager            — (exists, #29) Owns the slow environment mood cycle — every `AmbienceData.cycleIntervalSeconds`, advances sequentially through a tunable preset list, swapping `RenderSettings.skybox` (instant) and crossfading the ambience track (via `SoundManager.PlayAmbience`) together. Created via code by Bootstrapper, after `SoundManager` (needs a live reference to it)
└── UIManager                  — (exists, #30) Owns the root Canvas (Screen Space – Overlay) and 5 reusable, auto-stacking HudRegion screen regions (top-right stack, top-left, top-center toggleable, bottom-left, bottom-right) plus a standalone center popup anchor, each optionally backed by a decorative SCI-FI UI Pack Pro frame from UIThemeData — the shell #31-#33 migrate the 9 existing bare-OnGUI HUDs onto (see UI System below). Populates no HUD content itself. Created via code by Bootstrapper as the literal first manager in Awake() — every HUD self-serves this reference via FindFirstObjectByType<UIManager>() the same way it already self-serves its own manager, and HUD creation is interleaved throughout Awake() (not batched), so UIManager must exist before Bootstrapper's first HUD creation call, which in practice means before every other manager too
```

Manager access pattern:
```csharp

private GridManager _gridManager;
void Awake() { _gridManager = FindFirstObjectByType<GridManager>(); }
```

### Grid & Placement System
- One shared grid underlies platform modules, containers, and conveyors — no independent placement systems per piece type. `GridConfig` (`Assets/Data/GridConfig.asset`) is the single source of truth for cell size, height, and rotation snap — both the Editor-time `PlatformGridPlacerWindow` (X/Z only, `Vector2Int`) and the runtime `PlacementManager` (3D, `Vector3Int` — `WorldToCell3D`/`Cell3DToWorld`/`SnapPosition3D`) read from the same asset, never duplicate the math. The two method sets are additive/parallel, not shared call sites — extending one never required touching the other's call sites.
- Cell size (`GridConfig.cellSize`, currently 4m) and cell height (`GridConfig.cellHeight`, currently 3m) are **placeholders, not verified values** — SpacePlatformKit pieces have non-uniform footprints (confirmed by inspecting raw mesh bounds), so both need checking against real piece dimensions in-editor and adjusting before being treated as settled.
- Every placeable should implement a common `IPlaceable`-style contract: footprint (cells), facing/rotation, live validity check (occupied/out-of-bounds/bad-adjacency) shown via ghost preview before confirming. **Not built yet** — both the Editor tool and `PlacementManager` only check a single cell (the piece's origin) against a simple occupied-cell set, not a real multi-cell footprint. Known, explicitly-deferred gap in both places, not a silent one.
- Anchoring is permanent until explicit player removal — nothing drifts, nothing free-floats off-grid. This is a hard design requirement (GDD Pillar 3: "Clean by construction"), not a nice-to-have — any placement path that can leave a piece off-grid or unconfirmed is a bug.
- Runtime placement (`PlacementManager`) is **support-required and auto-stacking** (#3, reversing #1's original freeform-for-now decision after playtesting): a piece always snaps onto the deck (height level 0) or directly atop whatever's already placed in its aimed X/Z column — the player never chooses height directly, so a floating/unsupported piece can't be confirmed. Height is derived from `GridManager.NextFreeHeightLevel` each frame, not raycast against real platform geometry — deck-level (height 0) placement is valid anywhere in grid bounds without checking whether platform mesh actually exists there; that check is a separate, not-yet-built feature. Removing a piece cascades upward, removing everything stacked directly above it in the same column, so a removal can never leave something unsupported. No stack-height cap yet.
- `GridManager` (`Assets/Scripts/Grid/GridManager.cs`) is the single shared occupancy authority as of #4 — both `PlacementManager` and `ConveyorManager` register/unregister/query cells through it, so two independently-input-driven placers can never confirm into the same cell. Each placer still keeps its own local piece dictionary (cell → placed `GameObject`) for hit-testing/removal — `GridManager` only answers "is this cell occupied," it doesn't own instances. **Any future third placer must do the same** — route occupancy through `GridManager`, never maintain an independent registry.
- `GridConfig.deckSurfaceHeight` (found and fixed post-#4, during manual playtest): height level 0 resolves to this world Y, **not** world Y=0. SpacePlatformKit floor pieces (`SpacePlatformLargeBlue`, confirmed via `MeshRenderer.bounds`) are pivoted at their own vertical center, not their base — placing a piece's pivot at raw Y=0 buried it halfway inside the deck slab instead of resting it on top. `Cell3DToWorld`/`WorldToCell3D`/`SnapPosition3D` all measure height levels from this offset now. The mouse-aim raycast plane in both `PlacementManager.UpdatePreview` and `ConveyorManager.RaycastDeckCell` was also moved to this height (previously `Plane(Vector3.up, Vector3.zero)`) — same bug, different symptom (aiming precision at oblique camera angles, not just visual burial). Current value (`0.6918354`) is measured from the one floor piece type in the scene; **re-measure if a different-height floor piece is introduced.**

### Camera System
- Resolves the GDD's camera Open Question as **free-orbit, perspective** (Shapez 2-style), not locked top-down — chosen because `PlacementManager` already supports vertical stacking, which a strict top-down view would occlude.
- A `CameraRig` transform (scene-placed, at platform origin) is the pan target; the scene's pre-placed `Camera` (tagged `MainCamera`, a child of `CameraRig`) is positioned each frame as a spherical offset from the rig (yaw/pitch/distance) and always faces it. `CameraManager` never destroys, recreates, or reparents that `Camera` — **this is a hard constraint, not a style choice**: `PlacementManager.Awake()` caches `Camera.main` once and never re-queries it, and since `Bootstrapper.CreatePlacementManager()` uses `AddComponent<PlacementManager>()`, that `Awake()` fires synchronously inline during `Bootstrapper.Awake()`. Swapping the camera out from under it would silently break placement/removal raycasting with no error.
- `CameraManager` has no dependency on `PlacementManager` — scroll is free for zoom at all times, including during placement mode, since placement height is derived from column occupancy rather than manual scroll input (#3). `Bootstrapper.Awake()` still creates `PlacementManager` before `CameraManager`, but that ordering is no longer load-bearing for either manager.
- All tuning (orbit sensitivity, tilt clamp, pan speed/bounds, zoom range, default framing) lives in `CameraConfig` (`Assets/Data/CameraConfig.asset`), same pattern as `GridConfig`.

### Conveyor System
- Directional belt segments moving goods between adjacent grid cells. First pass landed (#4): `ConveyorManager` (`Assets/Scripts/Conveyors/`) handles both placement input and belt movement in one class, mirroring how `PlacementManager` already combines both roles for containers rather than splitting into separate placer/manager classes.
- Placement is **drag-based**, up to 10 cells per run along whichever axis (X or Z) the drag moved further along — C toggles placement mode, Q/R cycle flow direction while dragging, PageUp/PageDown select the height level, release confirms. A run overlapping any already-occupied cell is rejected — *except* its own last cell, which may land on an existing conveyor cell (a merge junction; that cell's own flow direction is what continues, it isn't replaced), and a run whose flow would ever route back to the Receiving dock's output cell (traced forward through whatever it merges into) is rejected as backflow. Both checks (`ConveyorManager.IsRunValid`) are shared by the ghost preview and the actual confirm, so the preview never shows valid for a run that would really be rejected. **(#7)** — a deliberate override of Phase 1's original straight-line-only scope, made explicitly via `/ba`/`/arch` rather than silently: junction *merging* and multi-level stacking are Phase 1; full splitting (1-to-N output distribution) stays Phase 2.
- **Anchor-and-stretch placement (#10):** a confirmed drag registers every cell it touches in `_segmentFlowDirections`/`GridManager` as one `PlacedSpan`, exactly as before — goods movement, junction arbitration, and backflow prevention needed zero changes; only what gets visually instantiated per cell has ever changed. `ConveyorData` gained `beltPlatformPrefab`/`beltSystemPrefab`, replacing the old single `prefab` field entirely (not left alongside as dead weight).
  - **Which cells show a real `BeltPlatform` anchor is a topology-derived property of the whole network, not a per-drag decision** (post-#10 second follow-up fix, same-day live bug report — "still getting gaps on longer drags," which turned out to be two separate bugs at once, both below). The first implementation planted an anchor at literally every drag's own start/end cell, decided once at confirm time. That put a **redundant second platform at every point a player extended an existing run with a new drag** — the new drag's own start cell always got its own anchor regardless of what was already sitting right next to it — reading as a random-looking "bump" in an otherwise continuous belt. Fixed by making anchor placement purely derived from current flow-graph topology (`ConveyorManager.IsAnchorCell`, called from `RebuildBeltVisuals`, recomputed wholesale after every placement/removal like `RebuildDockConnectors`/`RebuildJunctionFeeders`/`RebuildMainLine`, #7): a cell only shows a platform if it's a genuine start (nothing feeds it), a genuine end (its flow doesn't lead to another registered cell), a junction (2+ feeders), or a bend (its single feeder's flow direction differs from its own) — every other cell is a plain interior cell of a straight run regardless of which drag placed it, so two separately-confirmed drags that end up adjacent collapse into one continuous-looking run instead of showing a seam. Since no drag-owned anchor list exists anymore, removal (right-click) now resolves a clicked `BeltPlatform` back to its cell (`FindCellForHitObject`, unchanged) and looks up which `PlacedSpan` owns that *cell* (`_cellOwnership`, new — a span now only tracks `Cells`, not `OwnedInstances`) — replacing the old `FindSpanForHitObject` (searched a span's own instance list directly, which no longer exists since no span owns any visual).
  - **Fill tiles are rebuilt network-wide** (post-#10 first follow-up fix, same-day live bug report): a `BeltSystem` fill piece is instantiated once per flow-connected cell-gap — a first implementation attempt only tiled *within* the single span just confirmed, leaving a visible gap wherever a belt was extended across more than one separate drag (the join between two spans belonged to neither one's own cell list). Fixed the same way as the anchor fix above (`ConveyorManager.RebuildBeltVisuals`, which now does both jobs in one wholesale rebuild — anchors and fill tiles were split across two separate methods only briefly, merged once both turned out to need the same "recompute from current topology" shape). Fill tiles aren't tracked in any `PlacedSpan` and aren't individually removable — right-click only ever targets a `BeltPlatform` anchor.
  - **Each fill tile is scaled per-edge to the real open gap, not instantiated at one fixed length everywhere** (post-#10 third follow-up fix, same live bug report's other half — "gaps on longer drags" specifically got *worse* the longer a drag was, which a redundant-anchor bug alone doesn't explain). Around the same time, the designer moved `BeltPlatform`'s four `Fin` meshes off of `BeltSystem` and onto `BeltPlatform` itself (fixed to the platform's own posts, permanently aligned — replacing an earlier, abandoned attempt to align `BeltSystem`'s own fins to whichever platform happened to be next to it in a given rotation, which produced mirror-opposite misalignment at the two ends of any run since both platforms share the same non-mirrored rotation). This meant `BeltSystem` no longer carries any fins of its own, so its un-scaled authored length (measured 3.4m, `BeltSystemNativeLength`) no longer matches either kind of gap it needs to fill: an edge between two `BeltPlatform` anchors has less open space than a full 4m cell gap (each anchor's own fins eat `AnchorFinInsetPerEnd` ≈1.015m into the gap on its side — measured via `PrefabUtility.InstantiatePrefab`/`Renderer.bounds`), while an edge between two plain fill cells (no fins on either end) has the full 4m open — and a single fixed-length tile can't fit both correctly at once. A short 2-cell drag (all anchor-to-anchor edges) or a chained pair of them looked fine; a longer single drag has interior fill-to-fill edges where the unscaled 3.4m tile fell ~0.3m short on each side — worse the more interior edges a longer drag had. Fixed with `ConveyorManager.FillTileLengthScale`/`CreateFillTile`, which scale each tile's local Z per edge to `(cellSize − appropriate fin inset) / BeltSystemNativeLength` — shrinking toward an anchor, stretching slightly (~1.18×) to fully close a fin-free interior gap. Live-verified via simulated Play Mode input + `Renderer.bounds` measurement — **incompletely**, as the next entry found the same day.
  - **Fill tiles were still centered at the flat midpoint between their two cells, which only closes the gap when both ends apply the same inset** (post-#10 fourth follow-up fix, same day — the length-scaling fix above was reported live as not actually resolved: "same click and drag and getting gaps," with a screenshot). The first verification pass of the length fix only spot-checked interior-to-interior tile boundaries (which happen to be correct, since a fill cell contributes zero inset on both its edges and the flat midpoint is already right for that symmetric case) and missed that an **anchor-to-interior** boundary was still open by a real, visible ~0.5m — confirmed two ways: a live user screenshot of a straight drag showing exactly the two gaps this predicts (one near each end of the run), and, once automated re-testing risked interleaving with the user's own concurrent live testing and produced unreliable results, by rendering the game camera to a `RenderTexture` and reading back pixel colors along the belt's centerline directly (`Texture2D.ReadPixels`) rather than trusting the flaky `Unity_Camera_Capture` MCP tool or bounds-only spot checks. Root cause: centering every tile at the plain midpoint of its two cells' positions is only correct when both ends apply the same inset (anchor-anchor or fill-fill) — an anchor-adjacent tile and its fill-to-fill neighbor disagree about where their shared fill cell's own boundary actually is, since the anchor-adjacent tile's flat-midpoint placement stops short on **both** its ends (not just the anchor end) even though only the anchor end should be inset at all. Fixed by computing each tile's boundary on each end as `cellCenter ± CellHalfExtent(thatCell)` (`CellHalfExtent`: `AnchorFinInsetPerEnd` for an anchor, `0` for a plain fill cell — a fill cell has nothing of its own to stop a tile short of its exact center) and centering the tile at the midpoint of those two real boundaries, not the two cells' raw centers — shifts only apply where the two ends disagree (anchor-adjacent edges), leaving the already-correct symmetric cases (anchor-anchor, fill-fill) untouched. Re-verified the same two ways (transform bounds now touch to within ~6mm — the residual matches a separately-known, negligible `EnergyConnector` child-offset artifact — and a full pixel-scan along the belt found zero deck-colored samples anywhere along its length).
- Goods in transit are real simulation objects (`GoodsAgent`, `Assets/Scripts/Goods/`), not a shader/UV-scroll illusion — they carry their defining `GoodsData` and current cell; `ConveyorManager` moves them toward the next cell each frame at `ConveyorData.beltSpeed` (cells/sec) — multiplied live by `UpgradeManager.ConveyorSpeedMultiplier` (#27, 1 if no tier purchased yet), the one call site both `AdvanceGoods`'s movement calc reads, so a purchase instantly speeds up every belt already placed, not just future ones; `Vector3.MoveTowards` clamps to the target cell regardless of magnitude, so an arbitrarily high multiplier can't overshoot a cell boundary or skip arbitration/occupancy checks — if that next cell is also a conveyor segment *and* isn't already occupied by a different `GoodsAgent` (`IsCellOccupiedByOtherAgent`, added post-#6 — a busy belt visibly queues single-file instead of silently overlapping goods on top of each other) *and*, if it's a junction cell, this agent currently holds the claim on it (see below), otherwise they hold in place (end of a run, blocked, or lost a junction). This matters for later storage queries and for holding mid-belt when a downstream container is full. Goods ride at `ConveyorManager.GoodsRestPosition(cell)` — the segment's own position plus `ConveyorData.goodsRideHeight` (measured to match `TurretPlatformFlyingBlue`'s own top surface) — not the segment's own hover height, so a base-pivoted goods prefab (`Pallet1`) visibly sits on top of the segment instead of sinking into/behind its larger mesh.
- **Junction arbitration (#7):** a junction cell is purely a derived property of the flow-direction graph — any cell fed by 2+ other segments (`ConveyorManager.RebuildJunctionFeeders`, recomputed on every placement/removal, no separate placement step creates one). Each tick, an unclaimed, currently-free junction grants a claim to one ready feeder (an agent settled at a feeder cell): the sole ready feeder wins outright; under real contention (2+ ready at once) the main line — traced forward from the Receiving dock's output cell, recomputed the same way (`RebuildMainLine`) — wins, *unless* it also won that cell's last contention, in which case a different feeder is favored (`PickFavoredFeeder`), so a continuously busy main line can't starve a side line forever. A claim persists across frames until its holder arrives (or is destroyed), so an in-flight agent is never re-arbitrated away mid-transit.
  - **Goods-type merge priority (#21):** before any structural (main-line) or fairness logic runs, `ResolveJunctionClaims` first narrows contending ready feeders down to whichever carry the highest `GoodsData.mergePriority` among them (`HighestMergePriorityFeeders`) — a strictly-higher-priority good wins the claim outright, even over a lower-priority main line, since it's the only candidate left standing. `PickFavoredFeeder` only ever runs against feeders tied at the top priority present (which is every ready feeder whenever nothing's been explicitly prioritized, since `mergePriority` defaults to `0`) — this keeps every pre-#21 junction byte-identical until a designer actually differentiates some goods' priority. Same shape as #17/#18's "specific beats wildcard" split-routing precedent, applied to merges instead of branches. Not to be confused with the Roadmap's Phase-2-reserved "priority/rush" (`CLAUDE.md`'s own Roadmap table) — that's a *future, unrelated* concept scoped to which Shipping *order* gets fulfilled first; `mergePriority` never touches `OrderData`/`ShippingManager`, it's purely local to conveyor junction contention.
  - **Same issue, bundled fix:** `PickFavoredFeeder`'s own fairness tiebreak had the identical N-way starvation bug #18 already found and fixed in the split-side `PickFavoredBranch` — it only ever avoided the single immediately-previous winner, degenerating to alternating between just the first two feeders a junction ever saw and starving a third+ side feeder indefinitely. Fixed identically: find the last winner's index within the current candidate list and advance to the next index, wrapping around, instead of a linear "first non-last" scan. Bundled into this issue per `/arch`'s condition, since it's the exact same method already being touched and the same test topology exercises both. Live-verified: built a genuine 3-feeder junction and confirmed the priority mechanism bidirectionally (swapped which good/feeder carried the higher priority twice; the higher-priority good's feeder won and passed through the junction first both times, regardless of feeder position) — the round-robin fix itself got a lighter live spot-check (confirmed no deadlock/crash under sustained contention) rather than a full sustained multi-cycle proof, since the test topology's own junction cell happened to flow onward into one of its own three feeder cells (an artifact of the specific test layout, not a product bug) and created a temporary self-blocking cycle that made extended round-robin cycling awkward to observe cleanly; confidence is otherwise high given the fix is a direct, line-for-line-equivalent port of #18's already fully-proven algorithm.
- **Multi-level stacking (#7):** unlike `PlacementManager`'s auto-derived container stacking (#3 — the player never chooses height, it's always "next free level up"), conveyor height is player-chosen (PageUp/PageDown) — the entire point is deliberately routing at a chosen alternate level (flying over an obstacle), where "next free level" wouldn't make sense. This exposed a latent gap in `GridManager.NextFreeHeightLevel` (used by container placement): it computed `max(occupied.y) + 1`, which only ever matched "first free level from 0" because containers were the only thing that had ever used the Y axis and always stack contiguously from the bottom. An elevated conveyor with an empty deck cell below it broke that silently (containers could never land in the now-genuinely-free gap) — fixed to walk up from 0 and return the first actually-unoccupied level, verified behavior-preserving for every pre-#7 (contiguous-only) case.
- `ConveyorManager` still has an Editor-only debug spawn action (G, aimed at a placed segment) alongside the real `ReceivingManager` (#6) — a legacy manual-testing convenience now, not the real goods source.
- **Removing a segment loses any goods riding it** (`HandleRemoveInput` → `DestroyGoodsAtCell`, post-#5 polish, found via live playtest backpressure from ReceivingManager's constant spawn rate): previously, right-clicking a segment out from under a `GoodsAgent` only removed the segment — the agent itself was left behind, frozen forever, since `AdvanceGoods` can only move an agent off a cell it finds in `_segmentFlowDirections`, and a removed cell is gone from that dictionary. This silently orphaned goods (visible as pallets floating at conveyor height with no belt under them) any time a player rearranged a backed-up belt. Now any `GoodsAgent` whose `CurrentCell` matches the removed cell is destroyed along with the segment — a belt pulled out from under a good has nothing left to hold it up, so it's lost, matching how a full/misrouted good is already just left to sit rather than tracked as a failure state anywhere.
- **Splitting / type-filtered branching (#17)** — pulled forward from Phase 2 (a deliberate Roadmap override via `/ba`, same precedent as #7's junction merging, motivated directly by #15: choosing what Receiving delivers is only useful if it can be routed somewhere specific). A cell can now have 2+ outgoing directions — `_segmentFlowDirections` widened from `Dictionary<Vector3Int, Vector3Int>` to `Dictionary<Vector3Int, List<Vector3Int>>`; every pre-#17 call site degenerates to identical single-direction behavior when a cell's list has exactly one entry. A player creates a branch by starting a **second drag from an already-placed cell** in a new direction — `IsRunValid` gained a first-cell exception mirroring the existing last-cell merge exception (#7): the run's first cell may already be occupied if it's an existing segment whose direction list doesn't already contain the new flow direction. `ConfirmDrag` appends the new direction to that cell's existing list rather than registering a fresh cell, and records the addition in the placing `PlacedSpan`'s `OwnDirection` map (every (cell, direction) pair a span is responsible for, including a branch origin it doesn't fully own) — this is what lets `HandleRemoveInput`/`RemoveCells` take back only *their own* direction at a shared cell (`RemoveSpanDirection`) rather than risk unregistering a cell another span's branch still needs, the specific orphaning risk `/arch` flagged. `RebuildMainLine`/`TraceReachesReceiving` were widened from a single-path walk to a breadth-first reachability set over every branch (degenerates to the identical single-path result whenever no cell has more than one direction) — `PickFavoredFeeder`'s existing main-line-priority check reads this same set, unchanged. Each branch's accepted-goods filter is a `GoodsData` (null = "Any") keyed by the branch's own *destination* cell (not the shared split cell, which can't represent more than one filter at once) — assigned by clicking that destination cell outside both placement modes, cycling through the same content-derived choice list `ReceivingManager` already builds for #15 (`ReceivingManager.GoodsChoices`, a new public accessor, reused rather than re-derived). Each branch's arrow is also color-coded by its assigned filter (`ColorForBranchFilter`, found undocumented here during a later session when the designer asked whether this was a priority system — it isn't) — "Any" (null) stays the default amber `FlowArrowColor`, and any specific `GoodsData` gets a deterministic hue derived from `filter.GetInstanceID() % 360` via `Color.HSVToRGB` (so the same GoodsData asset always renders the same color, but which color is essentially arbitrary — not something a player configures or that encodes any importance/order). Applied only to a genuine split branch's own arrow (`IsSplitBranchDestination`, both at its `BeltPlatform` anchor and the `BeltSystem` fill-tile edge leading to it) — the shared split-origin cell itself stays untinted since it can't represent more than one branch's filter at once, and a plain unsplit run is never tinted at all, so color only ever appears where it's meaningful. Purely a visual "what is this branch filtered to" indicator — has zero bearing on `ChooseBranchDirection`/`PickFavoredBranch`'s actual routing precedence (specific-beats-wildcard, then round-robin among ties).
**`IsSplitBranchDestination` is an O(1) cache lookup, not a live network scan (#28).** Previously rescanned the whole `_segmentFlowDirections` graph on every single call — and `RebuildBeltVisuals` called it once per anchor cell *and* once per fill-tile edge (via `CreateFillTile`), making that method effectively O(n²) on a large branching network, a real per-placement cost confirmed by a proactive performance audit (not an observed problem). `RebuildBranchDestinationCells` now recomputes a persistent `_branchDestinationCells` `HashSet<Vector3Int>` once per `RebuildBeltVisuals` call, the same "topology-derived state, rebuilt wholesale on every rebuild" pattern `_mainLineCells`/`_junctionFeeders` already use (#7) — `IsSplitBranchDestination` itself is now just `_branchDestinationCells.Contains(cell)`, and every call site (the anchor tint check, `CreateFillTile`'s tint check, `HandleBranchFilterClickInput`'s click gate) benefits automatically since none of them changed. Live-verified: a real branch placed via simulated drag input rendered with the correct distinct tint and was correctly clickable to cycle its filter, console clean throughout.

A branch destination is always given a real `BeltPlatform` anchor by `IsAnchorCell` even when nothing else about it would otherwise qualify (a plain straight continuation) — not just for visual clarity, but because `BeltSystem` fill tiles carry **no collider at all** (the designer moved every `Fin` mesh onto `BeltPlatform` during #10), so a branch destination left as a plain fill cell would have nothing a raycast could ever hit. A `GoodsAgent` arriving at a splitting cell picks whichever branch's filter matches its own type (`ChooseBranchDirection`), breaking ties among 2+ matches via `PickFavoredBranch` (a simpler cousin of junction arbitration's `PickFavoredFeeder` — no main-line concept applies to an outgoing choice); the choice is cached per-agent (`_agentBranchChoice`) and cleared on arrival, the same persist-until-arrival shape `_claimedTargets` already established for junctions (#7), needed for the same reason — `CurrentCell` doesn't change until arrival, so recomputing the choice fresh every frame could flip an agent's target mid-flight. Live-verified: the regression baseline (a plain multi-cell run with no splits) renders and registers identically to pre-#17 behavior; branch placement (drag from an existing cell's middle in a new direction) was accepted, registered exactly the expected cell count, and rendered as a correctly-oriented T-junction with per-branch flow arrows; whole-span removal via right-click still works correctly post-#17. **Branch-level removal leaving a shared origin cell's other branch intact, and backflow prevention tracing through a branch, remain reasoned-through but not independently live-verified** — implementation confidence is high (`OwnDirection`-scoped removal, BFS degenerating correctly for the single-path case, both traced carefully against the actual pre-#17 code), but should still get a dedicated live pass before being treated as fully proven.
  - **Same-day follow-up fix, direct designer report:** type-filtered splitting "worked once, then stopped" — the main line backed up while a correctly-filtered branch sat empty. Root cause: `ChooseBranchDirection` treated a branch's unfiltered ("Any") destination as an equally-valid match against a *specific*-type branch for every good, so `PickFavoredBranch`'s fair-alternation between the two diluted routing — only a fraction of a given type's goods ever actually reached their intended branch, since alternation deliberately avoids repeating the same winner twice running. Fixed so a specific `GoodsData` match always wins over a wildcard; wildcards only compete among themselves, and only when nothing specific matches — the correct reading of "choose what item this branch carries," which should be deterministic once assigned. Live-verified this time with real goods (not just placement): 3 consecutive same-type agents spawned at a split with one branch specifically filtered and the main line left unfiltered **all** routed to the filtered branch, none leaked to the main line.
  - **Second follow-up fix, direct designer report (undeletable/regenerating pieces):** "if I remove the track, there is a left over piece... I can't delete these... the next belt I placed is a replica of the pieces I manually deleted." Root cause: `RemoveSpanDirection` unconditionally cleared `_cellOwnership[cell]` whenever the removing span was the current owner, even when the cell was still alive afterward because a *different* span's branch direction still lived there — `ConfirmDrag`'s branch-origin case (see above) deliberately never reassigns `_cellOwnership` when a new span merges onto an already-owned cell, so that second span's claim on the cell was never recorded anywhere. Once the *original* owning span was removed, the cell had a live direction but no owner at all — permanently un-targetable by `HandleRemoveInput` (which requires a `_cellOwnership` hit), and since `RebuildBeltVisuals` regenerates purely from `_segmentFlowDirections` (which never stopped believing the cell was occupied), manually deleting the GameObject in the Editor was undone by the very next placement anywhere on the network. Fixed by having `RemoveSpanDirection` search the other live `PlacedSpan`s for one that still holds a direction at the cell and reassign ownership to it, instead of leaving it orphaned.
  - **#18, Backpressure-Aware Throughput Splitting:** formalizes the *existing* unfiltered-branch ("Any") alternation into a real, backpressure-aware throughput divider — "a 60 PPM belt split N ways becomes N ~(60/N) PPM belts" — with no new placement mechanic, mode, or piece (a deliberate `/ba`/`/arch` decision: the primitive already existed as an unlabeled side effect of #17's tie-break, the real gap was fairness/backpressure, not a missing mechanic). Two real gaps found by `/arch` tracing the actual algorithm through 3+ sequential calls rather than trusting its generic `List<Vector3Int>` signature: (1) `PickFavoredBranch` only ever avoided the single immediately-previous winner, which degenerates to alternating between just the *first two* candidates a split ever saw — a third-plus branch was starved indefinitely. Fixed to real rotation: find the last winner's index in the current candidate list and advance to the next index, wrapping around, so N candidates cycle in sequence. (2) The proposed one-time "filter blocked candidates before the single per-agent `ChooseBranchDirection` call" only prevented committing to a branch that was *already* blocked at decision time — `_agentBranchChoice` caches permanently until arrival, so a branch that blocked *after* commitment (the realistic backpressure case) still stalled the whole split behind one committed agent. Fixed in `ResolveNextCell`: a cached choice is only trusted as-is once the agent has genuinely started moving (`transform.position` has left `GoodsRestPosition(CurrentCell)`); while still fully at rest, a blocked cached choice is discarded and re-decided fresh every frame — cheap and visually invisible, since nothing has moved yet — without spinning `PickFavoredBranch`'s shared per-cell fairness ledger on every idle frame (a genuine tie-break only fires when 2+ candidates are actually open at once; a single-open-candidate reroute returns directly). Live-verified via direct `RegisterGoodsAgent` spawns at a real, placement-built 3-way split (not just code review): three sequential agents visited all three branches exactly once each (proving the round-robin fix — the old algorithm would have repeated the first two branches and never reached the third), and a fourth agent that arrived when all three branches were simultaneously occupied correctly held in place, then immediately rerouted the instant one branch was freed while still stationary (proving the backpressure fix) — confirmed via a temporary diagnostic method added and removed for this verification pass, after an initial attempt using `Object.Destroy` on a blocking test agent produced a stale/inconclusive result (destroying an agent without also removing it from `ConveyorManager._activeGoods` leaves it readable by other code paths in ways that don't cleanly resolve to "gone" — relocating a live agent's cell via its own `SetCurrentCell`, not destroying it, is the clean way to free a cell in this kind of test).
- **Pre-drag hover ghost (#20):** closes a gap against this file's own Grid & Placement Convention ("ghost preview must reflect the real validity check... before the player confirms") — `PlacementManager`'s container ghost already showed this continuously from the moment placement mode is entered, but `ConveyorManager` previously showed nothing at all until the mouse was already held down for an active drag. `HandleDragInput` now calls a new `UpdateHoverPreview()` whenever placement mode is active but no drag has started (`!_dragStartCell.HasValue`) — confirmed via `/arch` that this needed **zero** new preview/validity machinery: `RebuildPreview` already produces a correct single ghost with a flow arrow and correct tint for a 1-element cell list (its anchor loop always instantiates index 0, its edge-fill loop naturally runs zero times for `lastIndex == 0`), `IsRunValid` already handles `Count == 1` correctly (index 0 is simultaneously the first-cell branch-origin exception and the last-cell merge exception), and `CancelDrag`/`DestroyPreviewInstances` already tear down any preview — hover or drag — on every mode-exit. `UpdateHoverPreview` is structurally identical to `UpdateDragPreview`, just with a computed 1-cell list instead of `ComputeDragRun`'s multi-cell run. The one real gap: `HandleHeightInput` previously only refreshed the preview when a drag was already started (`_dragStartCell.HasValue`) — extended to also call `UpdateHoverPreview()` when merely hovering, so PageUp/PageDown visibly updates the ghost's height immediately rather than only once the mouse next moves. Live-verified: the ghost appears the instant C is pressed with zero mouse movement/clicks, R correctly rotates its flow arrow pre-drag, starting a real drag replaces it cleanly with the existing multi-cell preview (no double-ghost), confirming a drag still places real segments identically to before, and exiting placement mode removes the ghost with the real placed belt left untouched.
- **Flow-direction indicator** (post-#6 polish): `TurretPlatformFlyingBlue`'s placeholder visual reads as roughly symmetric, so rotating it per `FlowRotation()` didn't actually communicate which way a segment feeds — players couldn't tell direction at a glance. Fixed with a small runtime-generated flat arrow (`AttachFlowArrow`, a procedural 2-triangle `Mesh` + `Universal Render Pipeline/Unlit` material, both built once and shared across every segment instance) parented under each segment — preview and confirmed alike — with identity local rotation, so it automatically points in the segment's flow direction by inheriting the parent's rotation rather than needing separate direction math. Destroyed automatically with its parent segment (no separate cleanup needed). Deliberately doesn't touch the shared `TurretPlatformFlyingBlue` prefab asset itself.
- **Energy connector, now dock-bridging only** (post-#6 polish, narrowed by #10): originally bridged the visual gap between *every* pair of connected segments with a procedural glowing quad — that segment-to-segment case is gone entirely as of #10, since a run's fill cells are now real placed `BeltSystem` pieces, not a gap needing a procedural bridge. The procedural connector (`RebuildDockConnectors`/`CreateEnergyConnector`, `Mesh` + `Universal Render Pipeline/Lit` material with `_EMISSION` enabled) now exists solely to bridge each dock's `ConnectionPoint` into the belt network, described next — it's no longer used anywhere else in the conveyor system.
- **Energy connector, dock bridging** (post-#9 polish, renamed `RebuildEnergyConnectors` → `RebuildDockConnectors` post-#10 to match its narrowed scope): the two docks are structurally opposite at their hand-off cell, so `ConnectLastSegmentToDock` (called twice from `RebuildDockConnectors`, once per dock via `ReceivingManager`/`ShippingManager`'s `GetPrimaryConnectionPoint()`/`GetPrimaryOutputCell()`/`GetPrimaryInputCell()`) branches on which shape applies. Shipping's input cell is deliberately never a real registered segment — `AdvanceGoods` treats it as a threshold where the good is handed to `ShippingManager` instead of continuing normal belt movement — so it never qualified for the segment-to-segment connector logic above; bridged with two hops (the real segment feeding it → the hand-off cell → the dock's `ConnectionPoint`). Receiving's output cell is the opposite: `ReceivingManager.HasSegmentAt` (its own earlier fix) gates spawning on a real segment actually placed AT that cell — it's the start of the belt run, not something with an upstream feeder, so the two-hop search finds nothing there; bridged with one direct hop (`ConnectionPoint` → that segment). No-ops if the relevant real segment doesn't exist yet or the dock hasn't registered. The connector quad's own mesh length is tuned for a one-cell (4m) gap — since a dock's `ConnectionPoint` can sit closer than that inside its compound prefab, `CreateEnergyConnector` scales the quad down (never up) to the real measured distance when it's shorter, so it can't overshoot into the dock's geometry. The dock-bridge endpoint is also flattened to the belt's own hover height (`FlattenToHeight`) rather than using the connector piece's raw (differently-pivoted) Y — otherwise the quad tilts like a ramp between the two different heights, which a low/oblique gameplay camera renders as a visibly skewed trapezoid even though the quad is a true rectangle in 3D. Deliberately left procedural — `/ba` scoped rebuilding this into another real `BeltSystem` piece as out-of-scope for #10, since `ConnectionPoint` sits at whatever offset the artist placed it inside each hand-built compound dock prefab, not a clean grid-cell distance a fixed-length tile could just be dropped into.
  - **Shipping's input cell must stay unoccupied by a real segment, unlike Receiving's** — the same asymmetry that drove the bridging logic above also breaks gameplay if violated: see the Shipping section below.
- **Belt speed upgrade purchase (#27):** Shift+left-click on any placed conveyor segment, outside both placement modes, attempts to purchase the next global conveyor speed tier (`ConveyorManager.HandleUpgradePurchaseClickInput`). Shift is a deliberate disambiguator, not an arbitrary choice — a plain click on a conveyor segment already meant two different things before this issue (left-click cycles a branch destination's goods filter, #17; right-click removes the whole span, #10), so neither free plain-click input existed for a third meaning. `HandleBranchFilterClickInput` gained a matching one-line early-return when Shift is held, so the two click handlers can never both fire off the same physical click. Live-verified via real simulated input (not just code review): a Shift+click on a plain segment purchased correctly (tier 0→1, money deducted, multiplier updated) without removing the segment or affecting any branch filter; a plain (non-Shift) click on the same segment afterward correctly did nothing (no second purchase).

### Upgrades (#27)
- Two global, retroactive upgrade tracks — conveyor belt speed and platform weight capacity — owned by `UpgradeManager` (`Assets/Scripts/Core/`), each a purchased-tier count against a fixed, ordered `UpgradeData` tier list (`multiplier`, `costMoney`). Both start at tier 0 (nothing purchased, multiplier 1) — purchasing spends money via `ScoreManager.TrySpend(int)` (new, the one spend path every purchase goes through) and, if affordable and not already at max tier, advances the tier index by one. Folds in and supersedes #8 (Conveyor Throughput Upgrades / PPM Tiers), whose own open questions (currency, purchase point, retroactivity, PPM-vs-`beltSpeed` mapping) this issue answers directly.
- **Deliberately global and retroactive, not per-piece:** `ConveyorManager`/`WeightManager` read the current multiplier live wherever the underlying stat is used (`AdvanceGoods`'s movement calc; `WeightManager.EffectiveCapacityKg`) rather than baking it into any per-segment/per-piece state — a purchase instantly affects every belt/segment already on the station, including ones built before the purchase and containers already carrying stored goods.
- **Two different purchase interactions for two different reasons:** belt speed is bought by Shift+left-clicking a placed conveyor segment (see Conveyor System above, for why Shift specifically). Platform capacity is bought by a plain left-click on a placed `PlatformSegment` floor tile, outside both placement modes — `WeightManager`'s first-ever per-frame input handling (previously purely reactive, notified only by `StorageManager` after deliver/withdraw) and its first-ever `SetGameActive(bool)`, now wired into `GameManager.EndRun`'s halt list alongside the other four managers so upgrade purchases stop once the run ends too. `PlatformSegment`'s prefab (`SpacePlatformLargeBlue`) already carries a working `MeshCollider` on the same GameObject the marker component sits on — confirmed by reading the prefab asset directly rather than assumed, resolving what `/arch` had flagged as a real open question (whether Editor-hand-placed platform geometry had ever needed to be raycast-hit-testable before, since every existing placement/aim raycast in the project targets a virtual ground plane, not real platform mesh).
- `UpgradeHUD` (`Assets/Scripts/UI/`) is a deliberately bare `OnGUI` readout of both tracks' current tier and next cost (or "MAX"), same Phase 1/2-stopgap convention as every other HUD.
- Live-verified end-to-end via real simulated input (not just direct API calls): a Shift+click purchase and a plain-click purchase each correctly advanced their own tier, deducted the correct cost, and left the other track/money untouched; `WeightManager.GetTotalCapacityKg()` read exactly 1.5× its pre-purchase value immediately after the platform tier purchase; a click attempted after `SetGameActive(false)` correctly no-op'd. **Not independently verified:** a precise "belt N× faster" timing ratio — `Unity_RunCommand`'s own round-trip latency exceeded the full traversal time of the short test run at every tier tried, so a clean before/after distance-over-time comparison wasn't obtainable this session; correctness here rests on the single, unambiguous multiplier read at `AdvanceGoods`'s one call site plus confirmation that movement/queueing/arrival all still worked correctly at a purchased (2×) multiplier, not on an independently measured ratio.

### Audio & Ambience (#29)
- `SoundManager` (`Assets/Scripts/Audio/`) is a general-purpose audio playback utility any system can call into — built around two already-imported third-party asset packs (**Universal Sound FX** for clips, **SpaceSkies 2** for skybox materials), neither previously referenced anywhere in this project. One dedicated, non-looping `AudioSource` per one-shot cue (placement confirm, placement reject, order fulfilled, order missed), played via `.Play()` — **not** `PlayOneShot`, a deliberate choice: `ConveyorManager.ConfirmDrag` raises `PlacementEventChannel.OnPiecePlaced` once **per cell** in a confirmed multi-cell drag (not once per confirm), so `PlayOneShot`'s overlapping-instance semantics would stack a 4-cell drag's confirm sound into an audible stutter; `.Play()`'s restart semantics collapse repeated calls within one frame into a single audible instance instead. Three of the four one-shot cues need zero new call sites anywhere — `SoundManager` subscribes directly to `PlacementEventChannel.OnPiecePlaced` and `OrderEventChannel.OnOrderFulfilled`/`OnOrderMissed`, the same direct-subscription pattern `ScoreManager`/`GameManager` already use for those exact channels. The one genuinely new call site is `ConveyorManager.ConfirmDrag`'s rejection branch (`_soundManager?.PlayPlacementReject()`) — containers can never reject a placement once a ghost is shown (`PlacementManager.TryConfirmPlacement` has no validity check at all, by construction of support-required auto-stacking, #3), so only conveyor drags can actually trigger this.
- **Belt hum is one shared, pooled loop, never per-segment** — `ConveyorManager.AdvanceGoods` reports its live `_activeGoods.Count` to `SoundManager.SetBeltActiveGoodsCount` once per frame (a trivial O(1) read, no new scanning), which starts/stops a single looping `AudioSource` and scales its volume between `beltMinVolume`/`beltMaxVolume` based on activity relative to `beltFullVolumeGoodsCount` — a deliberate choice to avoid the per-object cost this project's own #28 performance pass exists to eliminate.
- `AmbienceManager` (`Assets/Scripts/Audio/`) owns a slow environment mood cycle — every `AmbienceData.cycleIntervalSeconds`, advances sequentially (wraparound, not shuffled) through a tunable preset list, swapping `RenderSettings.skybox` **instantly** and crossfading the ambience track **over `ambienceCrossfadeSeconds`** via `SoundManager.PlayAmbience` (two alternating `AudioSource`s, one fading out while the other fades in) — together, so the two always change as one cohesive shift rather than two independently-ticking timers, per direct designer request. Deliberately does **not** touch `RenderSettings.skybox` on its own `Start()` — the scene already has a real skybox configured (`SampleScene`'s own Lighting settings already point at a SpaceSkies 2 material) — so the first real skybox swap happens at the first scheduled interval, same as every later one; ambience audio has no equivalent pre-existing state to preserve, so it starts crossfading in from silence immediately.
- **SpaceSkies 2's shader compatibility with URP was a real, checked risk, not an assumption** — every material in the pack uses Unity's built-in `Skybox/6 Sided` shader (confirmed via `Material.shader.name`), with no URP-specific alternative shipped anywhere in the package. Live-verified directly (not just `shader.isSupported == true`, though that also checked out): assigned two different SpaceSkies 2 materials to `RenderSettings.skybox` in a real Play Mode session and confirmed via screenshot that both render correctly — no pink/magenta/missing-shader placeholder.
- `SoundLibraryData.voiceLines` is a reserved, currently-empty `AudioClip[]` — no playback mechanism exists yet; recording real VO later is a content-only addition to this asset, not an architecture change.
- Live-verified end-to-end, all via real triggered actions (not just direct API calls where a real trigger was feasible): a real container placement played the confirm clip; a real conveyor drag through an occupied cell was rejected (existing `Debug.LogWarning` fired as before) and played the reject clip; a real `OrderEventChannel.OnOrderFulfilled`/`OnOrderMissed` raise played the correct clip on the correct dedicated source; `SetBeltActiveGoodsCount` produced exactly the expected `Lerp`-computed volume at 0/3/10 active goods and correctly started/stopped the loop; the environment cycle fired **twice** on its own during this session's live testing (this project's own recurring "real elapsed session time provides free verification" pattern, #24/#28) — `AmbienceManager.CurrentPresetIndex` advanced 0→1→2 exactly on schedule, `RenderSettings.skybox` matched the new preset each time, and the outgoing/incoming `AudioSource` pair correctly swapped (outgoing stopped at volume 0, incoming reached full target volume) confirming the crossfade coroutine ran to completion correctly.

### Storage System
- **First pass landed (#5).** Containers are placed via the same grid/placement system as everything else — `HangarBlue` replaced the old cardboard-box placeholder (`ContainerData_Hangar.asset`). `ContainerData` now carries `capacity` (`[Min(1)]`) alongside `displayName`/`prefab` — this resolves the GDD's container type-matching Open Question as a **per-instance identity lock**, not the full Phase-2 category taxonomy (a container locks to whichever single `GoodsData` it first accepts, not a category of several types).
- `StorageManager` (`Assets/Scripts/Storage/`) is the single source of truth for "what's stored where" — subscribes to `PlacementEventChannel.OnPiecePlaced` (its first real subscriber) and registers a placed piece only if it carries a `ContainerInstance` marker component, since that same event also fires for conveyor segments (`ConveyorManager.ConfirmDrag` raises it too) with nothing else in the payload to tell them apart. Exposes `TryStoreAt(cell, goodsData)` for `ConveyorManager` to call.
- `ContainerInstance` (attached by `PlacementManager.TryConfirmPlacement`, not part of the `HangarBlue` prefab itself) holds the per-instance state (`LockedType`, `CurrentCount`) and drives the door `Animator` directly via `Animator.Play(stateName)` — `HangarBlue` ships with a ready-made `HangarGrey` controller (`HangarClosed`/`HangarOpened`/`HangarOpen`/`HangarClose` clips) but **no exposed parameters**, so states are triggered by name, not `SetBool`/`SetTrigger`. Its default state (`HangarOpenCloseDEMO`, a demo loop) is overridden to `HangarClosed` on `Initialize()` — needed on both the real instance and the ghost preview (the preview instead just disables its `Animator` component entirely, since it shouldn't animate at all).
- `ConveyorManager.AdvanceGoods` hands a `GoodsAgent` off to `StorageManager.TryStoreAt` when its next cell isn't a conveyor segment (a container, most likely) — accepted removes the agent from tracking and destroys it (absorbed into storage); rejected (wrong type, full, or nothing there) just holds it in place, matching the existing end-of-run behavior. Needed a new `ConveyorManager` → `StorageManager` reference, wired by `Bootstrapper` after both exist — the original #5 spec (written before #4/#6 landed) didn't know this handoff didn't exist yet; caught by `/arch`.
- **Container removal never actually un-tracked the container in `StorageManager` (found and fixed during #14):** `PlacementManager.HandleRemoveInput` destroyed the container `GameObject` and unregistered its cell from `GridManager`, but never told `StorageManager` — `_containers` only ever had entries added (`HandlePiecePlaced`), never removed. A right-clicked-away container left a dangling `ContainerInstance` reference sitting in `StorageManager` until a *new* container happened to get placed at the same cell and silently overwrote the stale entry — a real, pre-existing bug independent of #14's own work, just never exercised until #14 needed a genuine `RemoveContainerAt(cell)` for its own segment-collapse path and the gap became unavoidable to fix. `StorageManager.RemoveContainerAt(cell)` is now the one real removal path; `PlacementManager` calls it via a new `SetStorageManager`-wired reference.
- **Storage output — a container can push goods back onto a belt (#22):** previously, storage was a one-way sink — `TryStoreAt` was the *only* way goods ever crossed a container's boundary, and the sole way stored goods ever counted toward anything was `ShippingManager` instantly crediting an order straight out of a container, no belt or Shipping dock involved at all. Direct user report ("in order to be counted toward a project the item(s) must be delivered to Shipping") removed that instant-credit path entirely — but since `StorageManager.TryWithdraw` had exactly one caller, deleting it outright would have made storage a permanent dead end (anything ever placed in a container could never count toward anything again), directly contradicting the GDD's own "Receive → Store → Ship" framing of the core loop. Resolved via `/ba` as storage gaining a real output side for the first time: `StorageManager.TryDispatch(goodsData, out spawnCell)` (replacing the old `TryWithdraw`) finds a container holding a matching, in-stock type with a real, currently-open conveyor segment against one of its four cardinal neighbors (checked in a fixed +X, +Z, -X, -Z order — new `StorageManager`↔`ConveyorManager` mutual reference, the same reciprocal-wiring shape `PlacementManager`/`ConveyorManager` already established for their own mutual reference, plus a new public `ConveyorManager.IsCellFreeForAgent`), withdraws only once a real destination is actually found, and reports the cell back. `ShippingManager.TryAutomaticDispatch` (renamed from `TryAutomaticWithdrawals`, since it no longer withdraws-and-credits in one step) spawns a real `GoodsAgent` there via the same `RegisterGoodsAgent`/`GoodsRestPosition` entry point `ReceivingManager` already uses — that good then travels and gets credited exactly like any other delivery, only ever through the unchanged `TryFulfillAt` arrival path. A container with no belt built against it simply doesn't dispatch — storage genuinely requires a return path now, not just an input one.
  - **A real correctness gap the spec didn't anticipate, found during `/dev`:** once `order.Deliver()` no longer happens at dispatch time (only at arrival), a naive `while (!order.IsFulfilled && TryDispatch(...))` loop would never see `IsFulfilled` advance within its own pass, and could dispatch far more units than an order still needs in a single frame (bounded only by how many of a container's four neighbor cells happen to be free belts at once). Fixed with a new `ActiveOrder.Reserved` counter — incremented on every successful dispatch, decremented on every `Deliver()` (a deliberate, safe approximation: any arrival closes out one reservation, not necessarily the exact unit that was reserved for it, so the worst case is dispatching one unit later than strictly necessary, never over-dispatching or getting stuck). `TryAutomaticDispatch`'s loop now gates on `Delivered + Reserved < requiredQuantity`, correctly re-checking after every unit exactly as the original spec's acceptance criteria intended.
  - **Known, accepted limitation (flagged by `/arch`, not fixed in this pass):** since a dispatched good must now physically travel rather than crediting instantly, there's a real window for an order's deadline to expire while it's still in transit. When it eventually arrives, `TryFulfillAt` finds no matching order and — existing behavior, unchanged — the agent just parks at the last real segment before Shipping's dock (its actual input cell is deliberately kept segment-free) and retries every frame forever, potentially blocking every other delivery behind it on that same approach. This is a **pre-existing** risk (already reachable via #13's escalating waves expiring mid-transit even before #22), just a meaningfully more likely one now that storage-to-Shipping trips can be longer than a direct Receiving line. Self-healing in most cases — `TryFulfillAt` re-scans *every* active order on every retry frame, so the parked agent unblocks the instant *any* order (including a later wave-generated one) ever wants that exact type again — but not guaranteed to clear. No despawn/timeout mechanism exists for this today; deliberately not built in this pass (no existing precedent to extend, and the risk is bounded/probabilistic rather than a hard bug) — worth revisiting if it's ever observed causing a real, persistent belt jam in play.
  - **Severe post-ship hotfix, same day, direct live bug report ("nothing is being pulled from storage"):** `FindFreeAdjacentBeltCell` originally only checked `HasSegmentAt`/`IsCellFreeForAgent` on a container's four neighbors — it never checked which way the candidate belt's own flow actually pointed. If a player builds an output belt whose flow (chosen independently via Q/R) happens to point back at the container it's adjacent to — e.g. by not cycling the direction away from whatever a previous drag last left it at — `TryDispatch` would withdraw a unit onto it, and `ConveyorManager.TryHandOffToDestination` (which fires the instant a next-cell lookup finds a non-segment cell, *before* any travel) would immediately hand that same unit right back into the same container on its very first `AdvanceGoods` cycle. Because `ShippingManager.TryAutomaticDispatch`'s loop only checks `Delivered + Reserved < requiredQuantity` (never container state), this became a silent, instant, zero-console-error round-trip that could burn through an order's entire `Reserved` capacity in a couple of frames while zero goods ever actually left — exactly matching the report, since nothing ever moved far enough to be visibly observed. Fixed with a new public `ConveyorManager.DoesCellFlowToward(cell, target)` (true if any of `cell`'s registered flow directions leads directly to `target`) and a matching `FindFreeAdjacentBeltCell` guard (`!_conveyorManager.DoesCellFlowToward(neighbor, containerCell)`) — a candidate neighbor must now both have free room *and* not flow straight back into the same container. Live-verified directly against `TryDispatch`/`DoesCellFlowToward` (not just code review): a container with only a backflow-flowing belt against it correctly dispatches nothing and keeps its stock untouched; the same container, once a second, correctly-outward-flowing belt existed on a different side, correctly dispatched onto that belt instead (confirmed via the real automatic per-frame `ShippingManager` path, not a manual call) and the resulting `GoodsAgent` held stably in place with no further container-count changes over several seconds — no silent loop.
  - **A second, separate, real cause of "nothing is being pulled" exists and was NOT fixed in this pass — height mismatch:** `FindFreeAdjacentBeltCell` only ever checks a container's four same-height cardinal neighbors (`containerCell + direction`, `direction.y` is always 0). A container stacked at height 1+ with a belt only built at height 0 silently never dispatches — no error, no console warning, indistinguishable from the bug above without direct inspection. This was an explicit "Out of Scope" line in #22's original spec ("Cross-height-level output") and is not being changed here; flagged because a player hitting either cause sees the identical symptom.
  - **A related, independent finding surfaced while reproducing the above, worth a dedicated look:** `HangarBlue`'s placed collider appears to extend past its own single grid cell into a neighboring cell's screen-space footprint from an oblique camera angle — a right-click aimed at an adjacent belt cell hit the container's collider first and `PlacementManager.HandleRemoveInput` silently deleted the container (no error, no confirmation), even though the click was nowhere near the container's own cell center. This is a specific, hit-testable symptom of this file's already-documented "occupancy tracking is one-cell-per-piece-origin, not real per-piece footprint checking" gap (see Grid & Placement System) — not new in kind, but newly confirmed to also cause **silent, unintended container deletion**, not just visual overlap. Not fixed in this pass; worth a footprint/collider-size check on `HangarBlue` specifically. **Confirmed still present when #23 (below) was implemented the next day** — right-clicking a belt cell diagonally/orthogonally adjacent to a container can still delete the container itself; worked around during that issue's live verification by avoiding any right-click near a placed container rather than by a code fix.
- **Fixed door/output sides — a container's rotation, chosen at placement, now determines which single side accepts input and which single side provides output (#23):** previously every one of a container's 4 cardinal neighbors could both feed it (`TryStoreAt`, direction-agnostic) and receive from it (`TryDispatch`'s `FindFreeAdjacentBeltCell`, looping all 4). Direct designer request ("the door is the received goods side, and the opposite side is the output... rather than a belt on any side") — resolved via `/ba`/`/arch` by making `PlacementManager`'s existing R-key rotation control (previously purely cosmetic — applied to `transform.rotation` at confirm time but never read back by any storage logic) functionally meaningful for the first time. `ContainerInstance.Initialize` now takes the confirming Y rotation directly and derives a new `DoorDirection` (`Quaternion.Euler(0, yRotationDegrees, 0) * Vector3.forward`, rounded to the nearest cardinal `Vector3Int`) — the exact same rotation math `PlacementManager` already applies to the instantiated GameObject's own transform, so the functional door side is guaranteed to agree with the visual one by construction, not a separately maintained lookup table. Confirmed live by directly measuring `HangarBlue`'s own `HangarDoor` child mesh's world offset from the container's center post-placement (not just the rotation math in isolation) — at each of the 4 rotations the door mesh's real offset exactly matches the computed `DoorDirection`.
  - `StorageManager.TryStoreAt(cell, goodsData, fromCell)` gained a `fromCell` parameter (`ConveyorManager.TryHandOffToDestination` already has the agent's own `CurrentCell` in scope, so this needed zero new tracking state) and now rejects any arrival where `fromCell != cell + container.DoorDirection` — exactly like a wrong-type/full rejection, holding the agent in place with no new failure state. `TryDispatch`'s old 4-direction `FindFreeAdjacentBeltCell` loop is replaced by `FindFreeOutputBeltCell`, which checks exactly one cell (`containerCell - DoorDirection`) — the existing `DoesCellFlowToward` backflow guard from the #22 hotfix still applies verbatim to that single candidate, unchanged in logic, just no longer looped.
  - **Deliberately not built:** post-placement re-rotation (a container's door is fixed the moment it's confirmed — to change it, remove and re-place, matching this project's existing "placement is permanent until explicit removal" rule) and blocking belt placement against the two non-door/non-output side faces (a belt can still be freely placed there, it's just functionally inert — matching how a belt dead-ending into open space already behaves). Both were explicit, designer-confirmed fork choices, not oversights.
  - **A real, designer-acknowledged breaking change:** every container placed before this shipped keeps whatever rotation it happened to have when confirmed (rotation was purely cosmetic until now) — its functional door/output sides are retroactively fixed to that rotation, which may not match belts already built around it in an ongoing session. No migration/prompt exists for this; the designer accepted the tradeoff explicitly during `/ba`.

### Weight & Platform Failure
- **First pass landed (#14).** Each platform floor segment (the individual `SpacePlatformLargeBlue` tiles the station is built from) has a maximum weight capacity (`PlatformSegmentData.capacityKg`, one shared asset for now — every current piece is the same type). `WeightManager` tracks each segment's current weight — the combined `GoodsData.weightKg * count` of everything stored in containers sitting on it — notified by `StorageManager` after every `TryStoreAt`/`TryWithdraw` via the delta between `ContainerInstance.CurrentWeightKg` before and after. **Goods in transit on a conveyor never count** — only goods actually stored in a placed container. Height level never matters for which segment a cell belongs to (a segment is a floor tile; stacked containers at any height on the same X/Z column all bear down on it) — deliberately X/Z-only.
- **Crossing capacity is immediate and local, not a run-ending event** (a conscious, designer-confirmed override of GDD Pillar 1's "not a puzzle game about clever constraint-solving under scarcity" — flagged explicitly during `/ba` and `/arch`, not a silent addition): every container, its stored goods, and every conveyor cell physically on the failed segment are destroyed (`StorageManager.RemoveContainerAt` + `GridManager.Unregister` for containers; `ConveyorManager.RemoveCells` for conveyor cells, which already handles its own unregistering and drops any riding `GoodsAgent`). Segments elsewhere are completely unaffected.
- **The floor piece itself is destroyed too, not just its contents (post-ship correction, same day):** #14's first pass kept the tile and only wiped what was built on it, since the original spec's "rebuild there... if they want to use that tile again" language implied the floor persisted. Direct designer feedback ("the platform that becomes overweighted should disappear all together") corrected this — `WeightManager.CollapseSegment` now also `Destroy()`s the `PlatformSegment` `GameObject` and permanently blocks its **entire** X/Z footprint in `GridManager` (every cell in the segment's measured bounds, not just ones that happened to hold a container/conveyor — computed via the same `FindSegmentForCell` bounds-containment check used for weight attribution), at every height level a player could plausibly reach (`PermanentlyBlockedHeightLevels = 20`, generous headroom, not a measured limit). Permanently blocking — never freeing — those cells matters because this project has **no runtime floor-placement mechanic**: platform assembly is Editor-time only (see Platform Assembly above), so once a tile is gone there is no way for a player to ever get a floor back there during a session; leaving the cells simply "free" would let a container/conveyor be confirmed floating over open space, a direct Pillar 3 ("clean by construction") violation. Live-verified: the collapsed area renders as a literal hole straight through to the starfield backdrop, matching the GDD's own "open space, no atmosphere" setting description.
- **Cell-to-segment ownership is resolved by measuring real geometry, not a footprint-in-cells formula** — a deliberate deviation from the original spec's Data Model (which proposed `PlatformSegmentData.footprint` in cells): `WeightManager.Initialize` measures every `PlatformSegment`'s actual `Renderer` bounds (X/Z) once at startup, and resolves a cell to whichever segment's bounds contain that cell's world position. Chosen because the real piece spacing doesn't divide as cleanly as the nominal 2×4-cell math suggests — a single `SpacePlatformLargeBlue`'s own measured bounds actually cover a 3×5-cell area (15 cells), not 2×4 (8), due to the kit's built-in joint overlap between adjacent pieces (confirmed by direct measurement, not assumed) — matching this project's established practice of measuring real geometry over hand-derived formulas. A cell sitting exactly on the overlap between two adjacent segments' bounds resolves to whichever segment is found first — a minor, acceptable ambiguity at the shared edge, not a correctness bug (every cell still resolves to exactly one segment).
- **`ConveyorManager` gained its first partial-removal capability (#14):** every prior removal path (`HandleRemoveInput`) operates on a whole `PlacedSpan` (per #10's own deliberate fix — see Conveyor System below), which would be wrong here: a segment collapse must destroy only the conveyor cells on the failed tile, potentially a small slice of a much longer run that continues onto healthy segments elsewhere. `RemoveCells(IEnumerable<Vector3Int>)` removes an arbitrary set of cells, trims (rather than deletes) any `PlacedSpan` that keeps some cells outside the removed set, and re-runs the same `RebuildBeltVisuals`/`RebuildNetworkTopology` pipeline afterward — live-verified with a 5-cell run spanning two segments: collapsing one segment removed exactly the one cell on it and left the other four (on the healthy neighboring segment) fully intact.
- `WeightHUD` (`Assets/Scripts/UI/`) is a deliberately bare `OnGUI` readout — one line per segment at or above 75% capacity (`WeightManager.GetSegmentStatusesNearCapacity`), so the display only ever shows segments that matter, not all of them all the time. A real styled HUD is Phase 2 UI polish, same as `ShippingHUD`/`GameOverHUD`.
- `WeightManager.GetTotalCapacityKg()` (#26) sums every currently-surviving segment's capacity — its first consumer outside this file, `ShippingManager`'s Special-event weight-target sizing (see Receiving & Shipping below). Computed fresh each call, never cached, so a platform that's already lost segments to overload correctly yields a smaller total.
- **Platform capacity upgrades (#27).** `WeightManager.EffectiveCapacityKg(segment)` is the one place every capacity read in this file goes through — a segment's raw `PlatformSegmentData.capacityKg` times `UpgradeManager.PlatformCapacityMultiplier` (1 if no tier purchased yet). Used by both the collapse check (`NotifyContainerWeightChanged`) and `GetTotalCapacityKg()`/`GetSegmentStatusesNearCapacity()`, so a purchased tier raises every segment's failure threshold instantly, including ones already carrying stored goods — live-verified: `GetTotalCapacityKg()` read exactly 32000kg pre-purchase and exactly 48000kg (32000 × 1.5, the first tier's multiplier) immediately after a real simulated click purchased it. `WeightManager` gained its first-ever per-frame input handling for this issue — a left-click on a placed `PlatformSegment` floor tile, outside both placement modes, attempts the next platform-tier purchase (`Update()`, new `_placementManager`/`_mainCamera` fields) — and its first-ever `SetGameActive(bool)`, now included in `GameManager.EndRun`'s halt list alongside the other four managers, so upgrade purchases stop working once the run ends too.

### Receiving & Shipping
- **Receiving — first pass landed (#6).** `ReceivingManager` spawns `GoodsData`-defined goods at `ReceivingDock`s on a fixed, tunable rate (`ReceivingData.itemsPerMinute`) — ramping that rate over a session (GDD's open question) is deliberately still unresolved, flat rate only for now. `ReceivingDock` is a **fixed, Editor-placed** component (resolved via `/ba` against the GDD's own "fixed dock" language, not a runtime-placeable piece like containers/conveyors). Output cell is one cell in front of `ConnectionPoint`, per its facing (`GetOutputDirection()`) — see the flush-connection note below for why this is one cell out, not `ConnectionPoint`'s own cell. Backpressure is handled by `ReceivingManager` tracking its own last-spawned agent per dock and skipping a spawn while it's still sitting on the output cell, rather than adding a new query method to `ConveyorManager`.
- **Shipping — first pass landed (#9).** `ShippingManager` owns the Company's order queue — a data-driven schedule (`ShippingScheduleData.scheduledOrders`, an ordered array of `OrderData`) where each order activates independently `startDelaySeconds` after game start and expires `deadlineSeconds` after its own activation, so multiple orders can be active concurrently rather than strictly one-at-a-time (a deliberate override of the simpler "one active order" default, made explicitly via `/ba` rather than assumed). `OrderData` is single-goods-type-only for Phase 1 (`requiredGoods`/`requiredQuantity`) — an order needing several types at once is Phase 2 "order complexity." `ShippingDock` mirrors `ReceivingDock`'s fixed/Editor-placed pattern exactly. Its input cell IS `ConnectionPoint`'s own cell (post-#9 fix — see below), reserved with `GridManager` so a real segment can never occupy it. Fulfillment — since #24 — credits whichever active order needing that goods type is *closest to finishing* first (see Order Tiers below), and — since #22 — only ever happens one way in truth: a `GoodsAgent` physically arriving at a dock's input cell via conveyor (`ShippingManager.TryFulfillAt`, tried by `ConveyorManager.AdvanceGoods`'s hand-off chain right after the existing container attempt — a cell is never both, so trying both in sequence is safe). A second, *automatic* path feeds that same arrival check rather than bypassing it: `ShippingManager.TryAutomaticDispatch` finds a container holding a wanted type with a real belt against one of its sides (`StorageManager.TryDispatch`) and spawns a real, traveling `GoodsAgent` there — it does not credit the order itself. Before #22, automatic withdrawal credited an order the instant a matching unit existed anywhere in storage, no belt or Shipping dock involved at all; see Storage System below for the full mechanic and its one known, accepted limitation. `OrderEventChannel` (new, mirrors `PlacementEventChannel`'s exact shape) raises `OnOrderActivated`/`OnOrderFulfilled`/`OnOrderMissed` — subscribed by `GameManager` (#12) for the loss condition; no `ScoreManager` yet. `ShippingHUD` (`Assets/Scripts/UI/`) is a deliberately bare `OnGUI` readout of active orders' progress, explicitly a Phase 1 stopgap, not the real (Phase 2) styled HUD.
- **Order Tiers — first pass landed (#24), Phase 2.** `OrderData` gained a `tier` field (`OrderTier`: `Priority`/`Random`/`Special`, `Priority` first/default so every existing authored asset and every wave-generated order defaults correctly with zero re-authoring) — the first piece of a larger Phase 2 arc splitting orders into the Company's endless demands (Priority — today's escalating-wave system already *is* this, just now explicitly labeled), player-opt-in paid odd jobs (Random), and rare huge weight-capacity-driven orders (Special). Only `Priority` is behaviorally wired up so far: `GameManager.HandleOrderMissed` now gates its miss counter (and therefore the run's loss condition) on `order.tier == OrderTier.Priority` — `Random`/`Special` misses, once those tiers exist, will cost the player a reward, not the run. Separately, `ShippingManager.OrdersByPriority()` (a new private helper, called by both `TryFulfillAt` and `TryAutomaticDispatch` in place of their old plain `_activeOrders` scan) replaced the original oldest-activated-first fulfillment tie-break with closest-to-finishing-first (`Delivered / requiredQuantity` descending) — originally implemented as a fresh LINQ `OrderByDescending` view each call, deliberately *not* an in-place sort of `_activeOrders`, since that list is also `ShippingHUD`'s read-only display source and nothing asked for its on-screen order to change. Live-verified: `TryFulfillAt` still credits correctly end-to-end after the refactor; the tier gate correctly counts a Priority miss and correctly ignores Random/Special misses; the sort algorithm itself directly verified against a constructed 4-order scenario (67%/50%/0%/0%) confirming both the percent-complete ordering and the activation-order tie-break.
  - **Per-frame LINQ allocation removed (#28).** `OrdersByPriority()` ran unconditionally every frame (via `TryAutomaticDispatch`'s `Update()` call), making its LINQ chain's enumerator/comparer allocation the one continuous, never-stops allocation a proactive performance audit found in this project. Replaced with a reusable `_orderedOrdersBuffer` field (`List<(ActiveOrder Order, int OriginalIndex)>`, cleared and repopulated each call rather than replaced) sorted via `List<T>.Sort` — which, unlike the LINQ chain it replaces, is **not** a stable sort, so each entry's original `_activeOrders` index is carried alongside it and used as `CompareByPriority`'s explicit final tiebreak key, reproducing the same activation-order fallback the old stable sort gave for free. `OrdersByPriority()`'s return type changed from `IEnumerable<ActiveOrder>` to the reused tuple-buffer `List`, so both call sites' `foreach` deconstructs `(ActiveOrder order, int _)` now. Live-verified against a genuine real 4-order tie scenario (all Priority tier, all 0% delivered) that arose naturally during this session's own escalating waves — not constructed: delivering one unit credited the order with the lowest original activation index, exactly reproducing pre-#28 behavior. Cross-tier fulfillment precedence (e.g. "Priority always beats Random for the same goods type") is deliberately undefined — only Priority orders exist today, so there's nothing yet to rank across tiers. **Not yet done:** any actual Random or Special order generation, any currency/scoring system, any upgrade system, any tier-aware HUD display — all explicitly out of scope for this issue, each earmarked for its own future `/ba` pass.
- **Random events + the money resource — first pass landed (#25).** `RandomJobPoolData` drives a rotating pool of `poolSize` (default 3) candidate Random-tier job offers, generated the same way `WaveEscalationData` generates Priority wave orders — `ShippingManager.RefreshJobOfferPool` keeps every pool slot filled, replacing any offer whose own `offerLifetimeSeconds` expires unpicked, in place by index so a highlighted-offer index never needs reindexing as offers churn. Every offer (accepted or expired) is a `ScriptableObject.CreateInstance<OrderData>()` instance tracked in the same `_generatedOrders`/`DestroyIfGenerated` cleanup `SpawnWaveOrder` already established (#13) — required given this pool churns far faster than wave orders ever did (a real condition from `/arch`'s review, not an afterthought). Left-click on `ShippingDock`'s own geometry cycles which offer is highlighted; right-click accepts it — both gated outside both placement modes exactly like `ReceivingManager`'s dock click (#15), reusing `ShippingDock`'s previously-unused geometry with zero collision (confirmed live: right-clicking the dock to accept an offer with a container placed immediately adjacent left the container untouched). At most one Random order can be active at a time — a second accept attempt is a silent no-op, matching a rejected placement's own silent-decline convention. `OrdersByPriority` (#24) gained `tier` as its primary sort key (`OrderBy(tier).ThenByDescending(percentComplete)`, both stable sorts) — Priority now always wins over Random for the same goods type, confirmed live by crediting a Priority order while a competing active Random order for the identical goods type stayed untouched. New `ScoreManager` (`Assets/Scripts/Core/`, the slot `CLAUDE.md` reserved since #9) subscribes to `OrderEventChannel.OnOrderFulfilled` and awards `OrderData.moneyReward` only when `tier == Random` — confirmed live that a long chain of Priority-crediting deliveries left `Money` untouched, and it incremented exactly once, by exactly the fulfilled Random order's own `moneyReward`, the moment that order actually completed and was removed. `JobOfferHUD`/`ScoreHUD` are both deliberately bare `OnGUI` readouts, same Phase 1/2-stopgap convention as every other HUD. **Not yet done:** spending money (upgrades, issue 4).
- **Special events — first pass landed (#26).** `SpecialEventData` drives a single rare Special-tier offer, generated after `spawnIntervalSeconds` of cooldown once neither a pending offer nor an active bundle exists — its weight target is `weightFractionTarget` (default 0.99) of `WeightManager.GetTotalCapacityKg()` (new, sums every *currently surviving* segment's capacity, queried fresh so a platform that already lost segments to overload gets a correspondingly smaller target). Deliberately **not** appended into `RandomJobPoolData`'s own `_jobOffers` list — that list's `RefreshJobOfferPool`/expiry logic is hardcoded to the Random pool's fixed `poolSize`/`offerLifetimeSeconds` churn, and a Special offer follows a structurally different, independently-timed single-slot lifecycle (a real `/arch`-flagged condition, not an afterthought). Instead `ShippingManager.PendingSpecialOffer` (a nullable `SpecialOfferPreview` struct, mirroring `WeightManager.SegmentWeightStatus`'s own snapshot-struct pattern) is tracked separately, and `HandleJobOfferInput`'s cycle range simply extends one virtual slot past the Random pool's own indices (`index == JobOffers.Count` means "the Special slot") — one unified click-cycle-and-accept interaction for the player, two honestly-separate backends underneath. A pending offer persists indefinitely once generated (no separate expiry, unlike Random) — deliberately simpler, matching a rare/precious offer rather than a churning one. Accepting it splits the weight target and money reward evenly across `bundleSize` (default 3) ordinary `OrderData` instances (`tier = Special`, random goods type per order, quantity derived from that type's own `weightKg` so the *combined* bundle hits the target) — each one pays its own reward share as it's individually delivered (a deliberate simplification over a single dramatic lump-sum-on-full-completion payout, which would need real bundle-completion tracking for comparatively little benefit — total money earned is identical either way, and partial completion before a shared deadline still keeps partial credit). `ScoreManager.HandleOrderFulfilled`'s gate is now `tier != Priority` rather than `tier == Random` specifically, so a hypothetical fourth tier wouldn't silently need a third comparison added later. `GameManager`'s loss-condition gate and `OrdersByPriority`'s tier sort both needed **zero** changes — confirmed live, not just claimed: both already generalized correctly (Special already sorts last, already excluded from the miss counter) the moment real Special-tier orders existed to exercise them. Live-verified end-to-end: the weight target computed to the exact expected value (32000kg × 0.99 = 31680kg against this scene's real platform), bundle quantities matched `CeilToInt(targetShare / weightKg)` exactly for all three generated goods types, a Priority order was credited over a competing Special order wanting the identical goods type, and a Special-tier miss correctly left the missed-order counter untouched while a Special-tier fulfillment correctly paid its own reward. **Not yet done:** spending money (upgrades, issue 4); the escalating-difficulty curve for `weightFractionTarget` across repeated Special events (explicitly deferred, flat 0.99 every time for now).
- **Escalating order waves — first pass landed (#13).** Once every `ShippingScheduleData.scheduledOrders` entry has activated (`IsScheduleExhausted`, checked against the same `_activatedFlags` array `ActivateDueOrders` already maintains), `ShippingManager.GenerateWaveOrders` starts spawning additional orders on its own timer — a random `GoodsData` from `WaveEscalationData.goodsPool`, quantity rising and deadline/spawn-interval shrinking every wave (each floored: `minDeadlineSeconds`/`minSpawnIntervalSeconds`), via `ScriptableObject.CreateInstance<OrderData>()`. Generated orders are pushed through the *exact same* `ActiveOrder`/`OrderEventChannel`/fulfillment path as authored ones (`SpawnWaveOrder` calls the same `_activeOrders.Add`/`RaiseOrderActivated` `ActivateDueOrders` uses) — nothing downstream (HUD, `GameManager`'s miss counter, fulfillment) can tell a generated order from an authored one, by design. Since a generated `OrderData` isn't a project asset, `DestroyIfGenerated` (called at all three places an order can leave `_activeOrders` — missed, auto-withdrawn, or delivered via `TryFulfillAt`) destroys it via a small `HashSet<OrderData> _generatedOrders` membership check — this project's first runtime-created (not asset-loaded) `ScriptableObject` instances, and its first place that needed an explicit cleanup story for one, since escalation is deliberately unbounded/indefinite. Stays single-goods-type per order (same as authored `OrderData`) — multi-good composition is still real Phase 2 "order complexity," not something this issue touches. Live-verified: two full escalation waves observed with exactly the expected quantity/deadline math, and fulfilling a generated order removed it cleanly with no console errors.
- **Order Parts Guide — first pass landed (#16).** `OrderGuideHUD` (`Assets/Scripts/UI/`) is a bare, toggleable `OnGUI` reference screen (**P** to show/hide) listing every `OrderData` in `ShippingScheduleData.scheduledOrders` — display name, required goods, required quantity — plus a line naming the pool of goods types an escalating wave order (#13) might draw from, without per-wave quantities (those escalate procedurally, not worth listing exactly). Deliberately static-content-only for this first pass: no live fulfilled/missed/active status per order, which would need new public surface on `ShippingManager` beyond what exists today — a future enhancement, not core scope. Reads `ShippingScheduleData`/`WaveEscalationData` directly (the same Bootstrapper-level asset references `ShippingManager` itself uses); unlike every other bare HUD in the project it has no manager to `FindFirstObjectByType` for, so it gets its references via its own `Initialize()` call from `Bootstrapper` instead.
  - **Docks no longer reject placement flush against them, but the functional requirement itself stays one cell out** (post-#9 fix, direct user report — a player naturally tries to place a belt touching the dock and, before this fix, got rejected with no clear reason why): both docks used to reserve their own `ConnectionPoint` cell with `GridManager`, blocking placement there. **First attempt (reverted the same day):** moved the *functional* requirement itself onto `ConnectionPoint`'s own cell for Receiving, reasoning its mechanic (a real segment must exist wherever goods spawn) made a zero-cell gap free. This broke spawning for every belt already built the normal way — one cell out from the dock, exactly where a player naturally stops, and exactly where the requirement had always been — since a segment placed a habitual one cell out no longer satisfied the (relocated) gate. **Actual fix:** only *unreserve* `ConnectionPoint`'s own cell (for both docks) so clicking it is no longer rejected; the functional requirement stays exactly where it always was — one cell out for Receiving (matching `HasSegmentAt`'s gate, unchanged), and one cell out from Shipping's single reserved input cell (itself now `ConnectionPoint`'s own cell, collapsed down from the two separately-reserved cells #9 originally shipped with). A player is free to also place a segment on `ConnectionPoint`'s own cell if they want (harmless, redundant with the decorative connector piece already there) — they're just no longer forced to route around it or confused by an unexplained rejection.
  - **A script recompile during Play Mode can silently orphan an entire placed conveyor network** (found while diagnosing the fix above, on a live user session): `ConveyorManager`'s segment-tracking dictionaries (`_segmentFlowDirections`, `_segmentInstances`) are plain runtime fields, never re-populated from scene state — a domain reload wipes them same as any other manager's non-serialized fields (see the `Bootstrapper`/`ReceivingManager` staleness entries below), but unlike those, there's no `Initialize()`-time re-scan to recover from, because the placed segment `GameObject`s were never meant to be rediscovered after the fact. The result: every previously-placed segment keeps existing as a normal scene `GameObject` (visible, still collides), but is completely invisible to `ConveyorManager` — no flow, no connectors, and `GridManager`'s occupancy is wiped too, so a player could even place a duplicate segment on top of the "ghost" one without any rejection. **No code fix exists for this yet** — the only recovery is a full Stop/Play cycle (which cleanly destroys every runtime-created `GameObject`, ghosts included, since none of it is part of the saved scene) followed by rebuilding the belt from scratch. Flagged as a real, not-yet-fixed gap: mid-session script edits are not safe against a player's in-progress belt network, and should be batched/confirmed before applying when a live Play Mode session has real work in it.

### Run State / Loss Condition
- **First pass landed (#12), extended in #27.** `GameManager` (`Assets/Scripts/Core/`) owns the run's only loss condition so far — a hard cap on missed orders. Subscribes to `OrderEventChannel.OnOrderMissed` and counts; at `GameRulesData.maxMissedOrders` (a new minimal ScriptableObject, default 10 — the live scene's own asset is tuned to 100) it calls `SetGameActive(false)` on `PlacementManager`, `ConveyorManager`, `ReceivingManager`, `ShippingManager`, and (#27) `WeightManager` — each of those five gained that method for exactly this purpose (a one-line guard at the top of their own `Update()`, plus force-exiting any in-progress placement/drag for the two placers). No win condition, restart flow, or scoring beyond the raw miss count — all explicitly deferred. `GameOverHUD` (`Assets/Scripts/UI/`) mirrors `ShippingHUD`'s bare `OnGUI` pattern: a running miss counter in the corner, plus a centered "RUN OVER" message once the limit hits.
- **Created deliberately last in `Bootstrapper.Awake()`** — it's the one manager that needs four others to already exist (something to halt) rather than the usual one-or-two dependency chain. Its `OrderEventChannel` subscription happens inside `Initialize()` itself, not relying on `OnEnable()` alone — `Bootstrapper` creates every manager via `AddComponent()`, which fires `OnEnable()` synchronously *before* `Initialize()` sets real references (the same `Camera.main` timing pitfall #2 already established for `Awake()`; the fix here is the same shape, applied to `OnEnable()`/event subscription instead of a cached reference).
- Verified live: raising `OrderEventChannel.OnOrderMissed` ten times drove `MissedCount` to 10 and `IsGameOver` to true in one step (no off-by-one), and a subsequent C/Tab key press was silently ignored by both `ConveyorManager` and `PlacementManager` (`IsPlacementModeActive` stayed false on both) — confirming the halt actually reaches input handling, not just internal state.

## Key Conventions

### Unity 6 API
- Use `FindFirstObjectByType<T>()` — **not** the deprecated `FindObjectOfType<T>()`
- Use the new Input System — **not** legacy `Input.GetKey` / `Input.GetAxis`
- URP shaders only — no Standard shader materials

### Input System — current state
`PlacementManager` (#1) and `ConveyorManager` (#4) both poll the new Input System's low-level API directly (`Keyboard.current`, `Mouse.current`) rather than going through `InputSystem_Actions.inputactions`' formal action maps — this is still "the new Input System," just not the Actions-asset layer. Deliberate for now: no `PlayerController` exists yet to define a real "Gameplay" action map, and hand-editing the `.inputactions` asset's binding/composite structure without a live Editor to verify it against was judged too risky when this was first decided. **Revisit once a real `PlayerController`/action map exists** — at that point both managers' raw polling should move into a proper action map so it doesn't double-handle the same physical inputs as gameplay controls. Now two managers do this rather than one — if a third arrives, that's probably the trigger to finally build the action map.

**Current bindings** (container placement / conveyor placement are mutually exclusive, so `R` is shared without ambiguity — entering one mode always force-exits the other):
| Key/input | Container mode (`PlacementManager`) | Conveyor mode (`ConveyorManager`) |
|---|---|---|
| Tab | Toggle placement mode | — |
| C | — | Toggle placement mode |
| Left-click | Confirm placement | Start/continue a drag run |
| Right-click | Remove piece (cascades up the stack) | Remove single segment (no cascade) |
| R | Rotate ghost 90° | Cycle flow direction forward |
| Q | — | Cycle flow direction backward |
| PageUp / PageDown | — | Raise/lower the height level a new run is placed at (#7) |
| Escape | Cancel placement | Cancel in-progress drag |
| G | — | (Editor-only) debug-spawn a `GoodsAgent` at the aimed segment |

**Outside both modes** (`ReceivingManager`, #15): left-click on a registered `ReceivingDock`'s own geometry cycles the goods type it currently spawns forward, wrapping around. No-ops while either placement mode above is active, since left-click already has a meaning there.

**Outside both modes** (`ConveyorManager`, #17): left-click on a conveyor split's branch destination cell (always a real anchor, see Conveyor System) cycles that branch's accepted-goods filter through the same content-derived choice list #15 built, plus "Any." No-ops on any cell that isn't a genuine branch destination, and while either placement mode is active, for the same reason as #15's dock click above.

**Outside both modes** (`ShippingManager`, #25): left-click on a registered `ShippingDock`'s own geometry cycles which Random-tier job offer is currently highlighted (wrapping); right-click on the same geometry accepts the highlighted offer, a no-op if a Random order is already active. Same dual-gate as every other outside-both-modes dock/cell click above.

**Outside both modes** (`ConveyorManager`, #27): Shift+left-click on any placed conveyor segment attempts to purchase the next conveyor belt-speed upgrade tier. Shift disambiguates this from #17's own plain-left-click (branch filter cycling) and #10's right-click (segment removal) on the same object type — `HandleBranchFilterClickInput` explicitly skips when Shift is held so the two click handlers can never both fire on one physical click.

**Outside both modes** (`WeightManager`, #27): left-click on a placed `PlatformSegment` floor tile attempts to purchase the next platform-capacity upgrade tier. `WeightManager`'s first-ever per-frame input handling — same dual-placement-mode gate as every other outside-both-modes click handler above.

**Global, any time** (`OrderGuideHUD`, #16): **P** toggles a reference screen listing every authored order's required goods/quantity, plus the escalating-wave goods pool. Works even during either placement mode, since it's a passive display with no interaction of its own.

### Script Quality
- Every public method and every Unity message (`Awake`, `Start`, `Update`, etc.) **must** have an XML summary comment describing its purpose, parameters, and any side effects
- Scripts over ~150 lines should be audited — they are likely doing too much (SRP)
- Prefer many small focused components over one large script
- No `GetComponent<T>()`, `FindFirstObjectByType<T>()`, or any scene lookups inside `Update` / `FixedUpdate` — cache everything in `Awake`

### ScriptableObject-First Design
All of the following **must** live in ScriptableObject assets, never hardcoded:
- Goods definitions (`GoodsData` — display name, prefab, category, footprint)
- Container stats (`ContainerData` — capacity, footprint, Phase 2 accepted-goods filter)
- Conveyor stats (`ConveyorData` — speed, footprint)
- Order composition/timing (`OrderData` — required goods, quantities, deadline)
- Receiving spawn scheduling/pacing tuning

### Event-Driven Communication
| Situation | Use |
|---|---|
| Game state changes (Playing → Paused → RunSummary) | C# `event Action` / `event Action<T>` |
| Designer-wired Inspector callbacks | `UnityEvent` |
| Cross-system broadcasts (good delivered, order fulfilled, order expired, placement confirmed) | ScriptableObject event channel |

Always unsubscribe (`-=`) in `OnDisable` or `OnDestroy`.

/// <summary>

### Bare OnGUI HUD Convention (retired/historical as of #33)
**All 9 HUDs have migrated to styled UGUI/TextMeshPro** (#30-#33) — see UI System above for the real, current architecture (`UIManager`, `HudRegion`, `UIThemeData`, `HudTextFactory`). Nothing in this project draws via `OnGUI` anymore. This section is kept for its historical wordWrap/clipping lessons, which carried forward directly into `HudTextFactory.CreateLabel`'s defaults (`enableWordWrapping = false`, `overflowMode = Overflow` — TMP's equivalent of the `TextClipping.Overflow` fix documented below) — read it as background on *why* those defaults exist, not as an active convention new code must follow.

Every Phase 1 HUD so far (`ShippingHUD`, `GameOverHUD`, `WeightHUD`, `ReceivingHUD`, `OrderGuideHUD`, `ControlsHUD`) is a deliberately bare `OnGUI` readout, created via `Bootstrapper` alongside the real managers even though none of them is one — a real styled `UIManager` is Phase 2 UI polish. For any line whose text can grow with content (a goods/order display name, a list of goods, anything **not** a small fixed string) — set the `GUIStyle` to both `wordWrap = false` **and** `clipping = TextClipping.Overflow`. Found live twice in the same session (#15, #16): IMGUI's default label style word-wraps by default, which combined with a single-line-height `Rect` silently clips the wrapped remainder; `wordWrap = false` alone isn't sufficient either, since IMGUI still clips non-wrapped text at the `Rect`'s own edge by default. A `Rect` sized generously for today's content will silently truncate again the moment that content grows — which several of this project's own systems (#13's wave pools, #15's goods choices) are explicitly designed to do over time — so `TextClipping.Overflow` is the only setting that guarantees a line is never silently cut off. Verify any new OnGUI text via a real `ScreenCapture.CaptureScreenshot`-based Game View capture, not `Unity_Camera_Capture` — OnGUI never renders through a camera-based render.
- **Never cache a `GUIStyle` (or anything touching `GUI.skin`) as a `static readonly` field** (found live, #19): a static field initializer runs in the type's static constructor, which fires the moment the type is first touched (here, `AddComponent<T>()` inside `Bootstrapper.Awake()`) — entirely outside any `OnGUI` call. `GUI.skin` throws `UnityException: get_guiDepth is not allowed to be called from a MonoBehaviour constructor...` when accessed there, and since a failed static constructor is caught as a `TypeInitializationException` by `AddComponent`, the component gets created (the `GameObject` exists, `activeInHierarchy` is true) but silently ends up with `enabled = false` — no visible error unless the console is checked, and the HUD just never renders. Every HUD's `GUIStyle` must be constructed fresh inside `OnGUI()` itself (as `OrderGuideHUD` already did, correctly, before `ControlsHUD` briefly deviated from it) — the per-frame allocation cost is negligible for a Phase 1 bare HUD.
- **Label string caching, where the displayed value changes far less often than OnGUI itself fires (#28)** — `ShippingHUD`/`JobOfferHUD` both rebuild a per-line label string via `$"..."` interpolation on every `OnGUI` pass, but OnGUI fires multiple times per frame (Layout + Repaint) while the underlying data (a Delivered count, a whole-second countdown) changes at most once. Both now cache the built string per line and only rebuild when the inputs that actually determine it change. The two HUDs' caches differ in one important way: `ShippingHUD`'s is keyed by `OrderData` identity and **must be pruned** (subscribed to `OrderEventChannel.OnOrderFulfilled`/`OnOrderMissed`, mirroring `ScoreManager`/`GameManager`'s own subscription pattern) — `_activeOrders` grows and shrinks continuously over an unbounded-length session (escalating wave orders), so an unpruned cache would itself become exactly the kind of leak this pass exists to prevent. `JobOfferHUD`'s cache is keyed by pool **slot index** instead and needs no pruning at all — `JobOffers` is a fixed-size, in-place-replaced rotating pool (#25) whose length never changes at runtime, so the cache is naturally bounded. Live-verified via real screenshots across multiple real game-state changes (a real delivery, deadline countdown, job-pool rotation, highlighted-offer changes) that displayed text stayed live-accurate, never stale.

### Grid & Placement Convention
- Snapping is the only placement mode — no freeform position/rotation for gameplay pieces (platform modules, containers, conveyors).
- Ghost preview must reflect the real validity check (occupied cells, out-of-bounds, bad adjacency) before the player confirms — never allow a confirm that a subsequent frame could reject.
- Rotation snaps to grid-aligned facings only (typically 90° increments) — match whatever the SpacePlatformKit's own module grid uses, don't invent an independent rotation scheme.

## Unity MCP

This project is connected to the Unity Editor via the `unity-mcp` relay (`Unity_*` tools) **when a session has it available** — it's not guaranteed present every session (depends on whether the Unity Editor is open with the relay running and reachable from that session). Use it to enter/exit Play Mode, capture the scene/game view, and read the Editor console instead of asking the user to check manually. See the `run` skill for the standard verification loop — Storage Lord is a 3D project (not 2D top-down like other projects using this same pipeline) with a free-orbit perspective camera (#2, resolving the GDD's camera Open Question), so always prefer `Unity_Camera_Capture` for verification screenshots over `Unity_SceneView_Capture2DScene`.

**When unavailable:** `/run`, `/test`, and `/ux`'s visual pass all require it. Don't fabricate a result if it's missing — `/test` already has this rule built in (falls back to a flagged pass-through when no tests exist, never guesses PASS). `/ux` should do the same: if the issue has a real visual surface, a missing connection is an honest `UX RESULT: FAIL` with a clear "environment gap, not a code defect" note, not a skip. `/handoff` should treat that specific case as a pause for manual verification, not a mechanical dev-retry loop — retrying `/dev` can't fix a missing Editor connection.

**`PlayerSettings.runInBackground` must stay `true`** (set during #6's dev pass, persisted to `ProjectSettings/ProjectSettings.asset`) — without it, Play Mode's entire frame loop freezes at frame 0 (`Time.time` never advances) whenever the Editor window isn't OS-focused, which is *always* true for an MCP-driven session since nothing ever clicks into the Editor window. This silently broke more than it looked like: `Unity_RunCommand` calls still succeed and return real data (they run on the Editor's own update, not the Play Mode player loop), so a frozen Play Mode is easy to mistake for "nothing happening yet" rather than "nothing will ever happen." If a future session finds Play Mode state not advancing between calls (timers never firing, input simulation never registering), check this setting hasn't regressed before assuming a code bug.

**Interactive input CAN be simulated reliably** once the above is true — `UnityEngine.InputSystem.InputSystem.QueueStateEvent(device, new KeyboardState(...)/new MouseState{...})`, called via `Unity_RunCommand`, is consumed by the game's normal `Keyboard.current`/`Mouse.current` polling on the next real frame. This only works spread across *separate* `Unity_RunCommand` calls with real wall-clock time between them (e.g. a `Bash sleep 1`) — looping `Thread.Sleep`+`EditorApplication.QueuePlayerLoopUpdate()` *inside* one call does not work, since that blocks the same main thread the player loop needs to advance on. `Unity_RunCommand`'s dynamic-assembly sandbox still cannot use `System.Reflection` (throws an unexplained `NullReferenceException` even wrapped in try/catch) — that limitation is unrelated to this one and still stands.
