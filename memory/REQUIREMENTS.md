# Requirements

Cases where a stated requirement mapped unexpectedly to a final spec — logged by `/ba`.

### [2026-09-14] — BA — "Get a camera in place" → CameraManager spec with explicit input-collision resolution against PlacementManager
**Context:** #2, Free-Orbit Platform Camera. The ask was a one-line "get a camera in place, similar to Shapez/Shapez 2."
**Learning:** A short ask for a new input-driven system (camera) turned out to require grepping the existing input-handling system (`PlacementManager`) for its exact bindings (Tab, scroll, R, left/right-click) before the camera spec could even propose its own bindings — the real spec content ended up being as much about *avoiding collision with an existing raw-polling system* as it was about the camera itself. This wasn't visible from the ask or from `CLAUDE.md` alone; it only surfaced by reading `PlacementManager.cs` directly.
**Apply when:** Any new spec that adds mouse/keyboard input (camera, new tools, UI shortcuts) — check every existing manager that does raw `Keyboard.current`/`Mouse.current` polling (see `CLAUDE.md`'s Input System section) for binding collisions before drafting bindings, don't just design the new system in isolation.

### [2026-09-15] — BA — "Cargo needs something solid under it, stacks row 1/row 2" → PlacementManager rewrite that also touches CameraManager
**Context:** #3, Support-Required Auto-Stack Container Placement. The ask was a short description of the desired placement feel (support required, auto-stack on top), surfaced during a `/dev` bugfix session for an unrelated crash.
**Learning:** A placement-behavior-only-sounding ask ended up requiring a change in `CameraManager` too — removing manual scroll-height control means `PlacementManager` no longer needs scroll during placement mode, which removes the reason `CameraManager.HandleZoomInput()` suppresses zoom while `IsPlacementModeActive`. This mirrors the #2 learning (new input-driven asks require checking every existing raw-polling manager) but in reverse: here, *removing* one system's scroll usage was what created the follow-on change in another system, not adding a new binding. Also: this spec was requested mid-`/dev`-session as a design comment ("does this make sense") rather than a formal feature ask — routed to `/ba` per `CLAUDE.md`'s explicit rule that freeform-vs-support-below is revisitable only through a real BA pass, not silently mid-bugfix.
**Apply when:** When a spec removes or repurposes an existing input binding (not just adds one), check other systems that key behavior off that same input's *mode/state* (e.g., `IsPlacementModeActive`), not just other systems that poll the same key/axis directly. A conversational "does this make sense" aside during an unrelated `/dev` session can still be a real spec-worthy ask — don't wait for a formally phrased feature request.

### [2026-09-15] — BA — "Conveyor system + type-locked storage" → 2 sequenced issues (#4, #5) plus a surfaced hidden prerequisite (no goods concept exists)
**Context:** Ask bundled two player-facing systems (belt placement/movement, type-locked containers) with two named placeholder assets for "our floating conveyor system." Neither ask mentioned that `GoodsData`/any goods object doesn't exist in the codebase yet — containers currently only carry a display name + prefab, no contents tracking at all.
**Learning:** A request phrased entirely in terms of two end-user-visible systems concealed a shared, unstated prerequisite (a goods concept) that both systems needed before either could be testable. Reading `CLAUDE.md`'s Proposed Manager Hierarchy against actual files (`Glob` on `Assets/Scripts/**/*.cs`) turned up `StorageManager` as still-not-started, which made clear the "type-locked storage" ask was really asking to build that manager, not just add a filter field. This surfaced as its own scoping addition (minimal `GoodsData` + debug spawn stub, flagged as temporary) rather than being assumed — and the two systems were sequenced as dependent issues (#5 depends on #4) rather than one issue, since #5's door-animation trigger needs #4's conveyor-adjacency detection to exist first.
**Apply when:** When two systems are requested together and one is described as feeding the other (conveyor → storage), check whether the *object* being fed (here: goods) actually exists in code yet — don't assume a noun used casually in the ask ("items," "goods") is already a real thing in the codebase. Cross-reference `CLAUDE.md`'s Proposed Manager Hierarchy against `Glob` of actual files before scoping, since a request can silently require standing up a manager the doc lists as "proposed."

### [2026-09-17] — BA — "Five numbered conveyor behaviors" → 1 Phase-1 network spec (#7) + 1 Phase-2 stub (#8), with item 3's plain phrasing hiding a functionally significant fork
**Context:** #7/#8, Conveyor Networks. The ask was a flat numbered list (junction merge, backflow prevention, stacking, PPM upgrade tiers, priority/alternation traffic rule) with no phase framing at all — items 1/2/4/5 turned out to be Phase 2 per `CLAUDE.md`'s own Roadmap ("junctions/splitters," "efficiency scoring"), item 3 was genuinely ambiguous.
**Learning:** Item 3, "belts can be stacked on top of each other," read casually as either purely cosmetic layering or a real functional multi-level routing mechanic (separate non-interacting Y-level lanes, extending `PlacementManager`'s existing container auto-stack precedent into `ConveyorManager`) — these two readings differ enormously in scope (one needs zero new code, the other needs new placement input, height-aware raycasting, and touches the core movement loop). Surfaced as an explicit fork rather than assumed; confirmed as the functional reading. Separately, item 5's "if all traffic is blocked, then it will alternate" clause was easy to read as a throwaway detail but is actually the spec's single most novel piece of state (per-junction fairness memory, no existing analogue anywhere in `ConveyorManager`) — worth its own dedicated fork question rather than folding into the general spec draft.
**Apply when:** A flat numbered list of behaviors from this designer should not be assumed to share one phase — check each item independently against `CLAUDE.md`'s Roadmap, even when they're phrased as one cohesive ask. When one item's wording could span a "trivial/cosmetic" reading and a "materially changes architecture" reading (stacking, but also watch for similar words like "connects," "syncs," "shares"), always fork it explicitly — don't let the simpler reading win by default just because the sentence was short. A one-clause aside buried at the end of a list item ("if all blocked, then it will alternate") can be the single most implementation-significant sentence in the whole ask — read every clause for hidden statefulness, not just the headline verb of each numbered item.

### [2026-09-17] — BA — "Objectives + mixed belts from receiving/shipping" → #9, a single-good order system where "mixed belt" is emergent, not a feature to build
**Context:** The ask for Shipping/Orders described projects needing specific parts, named two example goods (water, cement) as if one order might need both, and separately worried about "mixed items on a belt" as a problem to solve. Taken literally, this reads like it's asking for both multi-good orders (Phase 2 per `CLAUDE.md`) and some kind of belt-sorting/separation mechanic.
**Learning:** Neither literal reading was actually necessary once decomposed. A single-good-per-order model (confirmed via fork) still produces "cement now, water next" scheduling exactly as described, since multiple *concurrent, single-good* orders naturally create the mixed-belt problem across the whole network — the junction/routing system from #7 (already shipped) is what "solves" it, not new order-system code. The two named goods turned out to be flavor examples for variety, not a literal requirement that one order needs both simultaneously. Also: the codebase had exactly *one* `GoodsData` asset in it before this spec (`Pallet`) — an order system asking for "water vs. cement" implicitly required new goods content to even be testable, similar to the #4/#5 "goods concept didn't exist yet" gap.
**Apply when:** When a request names multiple example items for a system and separately describes a "conflict/mixing" problem between them, check whether the conflict is actually *emergent* from simpler, already-decided mechanics (here: multiple single-good orders sharing one belt network) before assuming a new mechanic needs to be built to resolve it. When a new content-driven system (orders, categories, recipes) is requested, check how many real instances of the underlying data type (`GoodsData`, here) actually exist in the project — a spec can silently need new content just to be exercisable, not just new code.

### [2026-09-18] — BA — "Get me the EnergyConnector as a prefab, I want to experiment" → full anchor-and-stretch placement rework, two sessions later
**Context:** A small, casual ask ("just get me the EnergyConnector as a prefab so I can adjust... I will build an example for your reference") turned out to be the first step of a much larger feature. Once the user had a real prefab to iterate on, they built `BeltPlatform`/`BeltSystem` themselves and came back with a fully-formed placement-UX change (#10) that replaces the very system the prefab was extracted from.
**Learning:** A request framed as "just give me an asset, out of curiosity" isn't necessarily scoped to stay small — when a designer asks for a raw asset extracted from a procedural system specifically so they can "experiment," treat that as a signal a bigger redesign of that system may follow once they've had time to iterate, not a one-off utility request to forget about. Also confirmed again (see `PATTERNS.md`'s dev-side entries from the same arc): the designer iterates by building real reference prefabs in-Editor before describing the feature in words, and the resulting spec should be checked against those prefabs directly (mesh bounds, child hierarchy, in-scene example) rather than taken only from the verbal description — a direct inspection pass this session caught a real technical fork (fixed-size `BeltSystem` end-caps vs. arbitrary stretch) the verbal description alone didn't surface.
**Apply when:** Don't treat "just give me X as a standalone asset" requests as scope-closed, especially when the stated reason is "so I can experiment/adjust" — check back in on what it was for once the user returns with something built from it. When a designer references their own hand-built prefabs as part of a spec, inspect them directly (hierarchy, bounds, an in-scene example if left) rather than relying on a screenshot or description alone — this designer's prefabs carry real structural information (fixed vs. stretchable pieces, embedded sub-components) that changes what's actually feasible to spec.

### [2026-09-20] — BA — "Random map generator, 60x60, events, lose at 10 misses, finish Storage Lord" (with blanket 24h approval) → three narrower Phase-1 specs, procedural generation and "events" resolved away
**Context:** User granted open-ended 24-hour approval and asked for a random map generator producing a >=60x60 scene with matching docks, a system of "unique events," and a 10-miss loss condition — framed as "finish Storage Lord," implying one continuous autonomous build. This bundled at least 4 distinct systems, two of which (true procedural generation, an undefined "events" system) aren't in the GDD/roadmap at all — not deferred-to-Phase-2 territory, genuinely unspecified.
**Learning:** Presented with three sharp forking questions (grid-cell vs. meter scale; true runtime procgen vs. one curated layout; what "events" means) rather than open-ended ones, the user picked the Recommended/lower-risk option on all three without hesitation — despite the enthusiastic, "go forth and conquer," approval-blanket framing of the original ask, they didn't push back on de-scoping true procedural generation down to a single hand-curated large layout, or "events" down to escalating order waves (the closest fit to existing `OrderData`/`ShippingScheduleData` systems) rather than a new hazards/disruption mechanic. The final three specs (#11 large curated layout, #12 loss condition/GameManager, #13 escalating waves) are all Phase-1-compatible; the two genuinely novel-sounding asks (procgen, events) evaporated into "reuse existing tooling/systems, just at larger scale/longer duration" once broken down.
**Apply when:** A large, enthusiastically-worded, "just go build it" request with blanket approval is exactly the situation to slow down and decompose *before* touching code, not the situation to skip `/arch` because the user seems to be granting permission to. This designer responds well to a small number of concrete, consequence-labeled forking questions (each option's tradeoff stated plainly) even when they've explicitly asked for autonomy — offering a clearly-labeled "Recommended" lower-risk default and letting them choose is not friction to them, it's exactly the signal they want before committing real time. When a request contains words like "random," "generator," "events," or "procedural," check first whether the *existing* systems can be stretched to deliver the same player-facing outcome (bigger curated content, existing order/schedule systems run longer/harder) before assuming a whole new system needs to be designed from scratch.

### [2026-09-21] — BA — "Add weight to platforms so they can fail, sort of a puzzle" → per-segment capacity/collapse system, scoped from four forks in one pass
**Context:** A short, casually-worded pitch ("now for the fun part... let's add in this system... I know we will need to add weight to each item and figure out the best place to calculate total weight") contained at least four independent unresolved forks: per-segment vs. whole-station capacity, run-ending vs. localized failure, goods-only vs. structures-too weight, and whether the capacity itself should escalate. It also — unprompted by the user — directly contradicted GDD Pillar 1's "not a puzzle game about clever constraint-solving under scarcity."
**Learning:** All four forks were resolved in a single `AskUserQuestion` round with a Recommended option on each, and the user took every Recommended answer, including the one (per-segment capacity) that most directly leans into the Pillar-1 conflict already flagged in the same message. The final spec (#14) stayed a single coherent issue rather than splintering into several — unlike the earlier 24-hour mega-request, this one was naturally sized once the forks were resolved, not artificially bundled.
**Apply when:** A short, casual-sounding feature pitch can still hide several real forks — count them explicitly before drafting (this one had four) rather than assuming brevity means the request is simple. When one of the forks is a genuine conflict with a stated Pillar/GDD principle (not just a phase-scope boundary), surface it in the *same* pass as the forking questions, not as a separate gate — this designer wants to make that call at the same time as the mechanical ones, not in a follow-up round.
