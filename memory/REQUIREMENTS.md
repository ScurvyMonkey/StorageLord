# Requirements

Cases where a stated requirement mapped unexpectedly to a final spec — logged by `/ba`.

### [2026-09-14] — BA — "Get a camera in place" → CameraManager spec with explicit input-collision resolution against PlacementManager
**Context:** #2, Free-Orbit Platform Camera. The ask was a one-line "get a camera in place, similar to Shapez/Shapez 2."
**Learning:** A short ask for a new input-driven system (camera) turned out to require grepping the existing input-handling system (`PlacementManager`) for its exact bindings (Tab, scroll, R, left/right-click) before the camera spec could even propose its own bindings — the real spec content ended up being as much about *avoiding collision with an existing raw-polling system* as it was about the camera itself. This wasn't visible from the ask or from `CLAUDE.md` alone; it only surfaced by reading `PlacementManager.cs` directly.
**Apply when:** Any new spec that adds mouse/keyboard input (camera, new tools, UI shortcuts) — check every existing manager that does raw `Keyboard.current`/`Mouse.current` polling (see `CLAUDE.md`'s Input System section) for binding collisions before drafting bindings, don't just design the new system in isolation.

### [2026-09-15] — BA — "Cargo needs something solid under it, stacks row 1/row 2" → PlacementManager rewrite that also touches CameraManager
**Context:** #3, Support-Required Auto-Stack Container Placement. The ask was a short description of the desired placement feel (support required, auto-stack on top), surfaced during a `/dev` bugfix session for an unrelated crash.
**Learning:** A placement-behavior-only-sounding ask ended up requiring a change in `CameraManager` too — removing manual scroll-height control means `PlacementManager` no longer needs scroll during placement mode, which removes the reason `CameraManager.HandleZoomInput()` suppresses zoom while `IsPlacementModeActive`. This mirrors the #2 learning (new input-driven asks require checking every existing raw-polling manager) but in reverse: here, *removing* one system's scroll usage was what created the follow-on change in another system, not adding a new binding. Also: this spec was requested mid-`/dev`-session as a design comment ("does this make sense") rather than a formal feature ask — routed to `/ba` per `CLAUDE.md`'s explicit rule that freeform-vs-support-below is revisitable only through a real BA pass, not silently mid-bugfix.
**Apply when:** When a spec removes or repurposes an existing input binding (not just adds one), check other systems that key behavior off that same input's *mode/state* (e.g., `IsPlacementModeActive`), not just other systems that poll the same key/axis directly. A conversational "does this make sense" aside during an unrelated `/dev` session can still be a real spec-worthy ask — don't wait for a formally phrased feature request.

### [2026-09-15] — BA — "Conveyor system + type-locked storage" → 2 sequenced issues (#4, #5) plus a surfaced hidden prerequisite (no goods concept exists)
**Context:** Ask bundled two player-facing systems (belt placement/movement, type-locked containers) with two named placeholder assets for "our floating conveyor system." Neither ask mentioned that `GoodsData`/any goods object doesn't exist in the codebase yet — containers currently only carry a display name + prefab, no contents tracking at all.
**Learning:** A request phrased entirely in terms of two end-user-visible systems concealed a shared, unstated prerequisite (a goods concept) that both systems needed before either could be testable. Reading `CLAUDE.md`'s Proposed Manager Hierarchy against actual files (`Glob` on `Assets/Scripts/**/*.cs`) turned up `StorageManager` as still-not-started, which made clear the "type-locked storage" ask was really asking to build that manager, not just add a filter field. This surfaced as its own scoping addition (minimal `GoodsData` + debug spawn stub, flagged as temporary) rather than being assumed — and the two systems were sequenced as dependent issues (#5 depends on #4) rather than one issue, since #5's door-animation trigger needs #4's conveyor-adjacency detection to exist first.
**Apply when:** When two systems are requested together and one is described as feeding the other (conveyor → storage), check whether the *object* being fed (here: goods) actually exists in code yet — don't assume a noun used casually in the ask ("items," "goods") is already a real thing in the codebase. Cross-reference `CLAUDE.md`'s Proposed Manager Hierarchy against `Glob` of actual files before scoping, since a request can silently require standing up a manager the doc lists as "proposed."

### [2026-09-17] — BA — "Five numbered conveyor behaviors" → 1 Phase-1 network spec (#7) + 1 Phase-2 stub (#8), with item 3's plain phrasing hiding a functionally significant fork
**Context:** #7/#8, Conveyor Networks. The ask was a flat numbered list (junction merge, backflow prevention, stacking, PPM upgrade tiers, priority/alternation traffic rule) with no phase framing at all — items 1/2/4/5 turned out to be Phase 2 per `CLAUDE.md`'s own Roadmap ("junctions/splitters," "efficiency scoring"), item 3 was genuinely ambiguous.
**Learning:** Item 3, "belts can be stacked on top of each other," read casually as either purely cosmetic layering or a real functional multi-level routing mechanic (separate non-interacting Y-level lanes, extending `PlacementManager`'s existing container auto-stack precedent into `ConveyorManager`) — these two readings differ enormously in scope (one needs zero new code, the other needs new placement input, height-aware raycasting, and touches the core movement loop). Surfaced as an explicit fork rather than assumed; confirmed as the functional reading. Separately, item 5's "if all traffic is blocked, then it will alternate" clause was easy to read as a throwaway detail but is actually the spec's single most novel piece of state (per-junction fairness memory, no existing analogue anywhere in `ConveyorManager`) — worth its own dedicated fork question rather than folding into the general spec draft.
**Apply when:** A flat numbered list of behaviors from this designer should not be assumed to share one phase — check each item independently against `CLAUDE.md`'s Roadmap, even when they're phrased as one cohesive ask. When one item's wording could span a "trivial/cosmetic" reading and a "materially changes architecture" reading (stacking, but also watch for similar words like "connects," "syncs," "shares"), always fork it explicitly — don't let the simpler reading win by default just because the sentence was short. A one-clause aside buried at the end of a list item ("if all blocked, then it will alternate") can be the single most implementation-significant sentence in the whole ask — read every clause for hidden statefulness, not just the headline verb of each numbered item.
