### [2026-09-14] — Dev — Platform Grid Placer (Editor-time level tool) + GridConfig
**Context:** First implementation on the project — grid & placement system, scoped down to "just get platform pieces placing on a grid" per direct user request (no formal GitHub issue for this one; went the `/dev` "Direct Request" path).
**Learning:** Resolved the CLAUDE.md-flagged open question "is platform assembly player-placed or hand-authored?" as **hand-authored, Editor-time** — built `PlatformGridPlacerWindow` (Window → Storage Lord → Platform Grid Placer) as a `SceneView.duringSceneGui`-driven tool, not a runtime MonoBehaviour system. Ground-plane raycast (`Plane(Vector3.up, Vector3.zero)` + `Ray` from `HandleUtility.GUIPointToWorldRay`) → `GridConfig.SnapPosition` → `PrefabUtility.InstantiatePrefab` (keeps the prefab link, unlike `GameObject.Instantiate`) parented under an auto-created `Platform` root. Occupancy is intentionally shallow for this pass: one grid cell per piece origin, reconstructed from existing children each time placement starts (no separate persisted state) — real footprint-aware occupancy needs per-prefab footprint data that doesn't exist yet.
Separately: SpacePlatformKit's FBX files turned out to be **ASCII-format** (Blender exporter, FBX 6.1), not binary — their raw `Vertices:` blocks are grep/awk-parseable for a rough bounding-box sanity check even without Unity itself running. Useful for spot-checking relative piece sizes, but the raw values are in FBX's native units/axes (unknown scale-factor/axis-conversion applied by Unity's importer), so they're not reliable enough to derive an authoritative `cellSize` in meters — don't present a number derived this way as verified without checking it against the actual imported piece in-editor.
**Apply when:** Before building the runtime `PlacementManager` for containers/conveyors, reuse `GridConfig`'s snap/cell-conversion methods rather than re-deriving grid math — that's the whole point of factoring it out now. If footprint-aware occupancy becomes necessary (multi-cell pieces overlapping), that's a real gap to close, not a nice-to-have — flag it rather than letting it silently stay single-cell.

### [2026-09-15] — Dev — #1 Runtime PlacementManager: height via a moving placement plane, raw Input System polling, material-tint preview
**Context:** First runtime manager in the project (`PlacementManager` + `Bootstrapper`), built per issue #1 and its arch review's two conditions (event channel, minimal Bootstrapper).
**Learning:** The "aim at a floating mid-air cell" problem (how do you target a stacked cell above another piece) is solved by raycasting against a horizontal `Plane` positioned at `heightLevel * cellHeight` — the plane moves with a scroll-controlled `heightLevel` int, independent of the X/Z screen-ray hit. This is the same ground-plane-raycast technique `PlatformGridPlacerWindow` already used (`Plane(Vector3.up, ...)` + `Raycast`), just with the plane's Y no longer fixed at 0 and driven by `Camera.main` instead of `HandleUtility.GUIPointToWorldRay`.
Deliberately used raw Input System polling (`Keyboard.current`/`Mouse.current`) instead of editing `InputSystem_Actions.inputactions` — still fully "the new Input System" per CLAUDE.md's convention, but sidesteps hand-editing a complex binding/composite asset with no live Editor to verify it against (much higher risk than the flat scene-YAML edits done so far). Logged as a CLAUDE.md-documented deviation, not a silent one — flagged there to migrate once a real `PlayerController`/action map exists.
Preview valid/invalid feedback uses `Renderer.material.color` (not `sharedMaterial`) — `.material` auto-clones per-instance on first access, so tinting the preview never touches the source prefab's actual shared material. Untested against real URP Lit materials in a live Editor (no Unity connection this session) — `Material.color` is documented to map to URP's `_BaseColor` for compatibility, but confirm visually before trusting it.
**Apply when:** Any future system needing to aim at a specific height/depth (not just X/Z) can reuse the moving-placement-plane pattern rather than inventing 3D cursor logic. Before adding more raw-polled inputs to `PlacementManager`, check whether a real action map has landed yet — if so, migrate rather than adding another one-off `Keyboard.current` call.

### [2026-09-15] — Dev — #3 Support-Required Auto-Stack Placement: derive height from occupancy, don't ask the player for it
**Context:** Reworked `PlacementManager` per #3/arch: replaced scroll-driven manual height with support-required auto-stacking, and removed the now-dead `CameraManager`↔`PlacementManager` coupling per the arch review's condition.
**Learning:** The raycast/height dependency inverts from the #1 version: previously the plane's Y came from player-chosen `_heightLevel` *before* raycasting; now height is unknown until *after* the X/Z column is known, so `UpdatePreview()` raycasts a fixed Y=0 deck plane first, converts to a `Vector2Int` column via `GridConfig.WorldToCell`, then derives height via a new `NextFreeHeightLevel(column)` — a linear scan of `_occupiedCells` for matching X/Z, returning `maxY + 1` (or 0 if none). Linear scan is fine at Phase 1 scale (per arch's Low-severity note) — no per-column index needed yet. Cascade-removal is a pure data walk: `for (cell = clicked; _placedPieces.ContainsKey(cell); cell += Vector3Int.up)`, no extra physics raycasts — this only works because placement/removal together maintain the invariant that each column's occupied cells are always contiguous from 0 upward (placement always fills the next level; removal always clears contiguously upward from the clicked cell), so a plain "does the next cell up exist" check can't skip a gap.
Removing `IsPlacementModeActive` from `PlacementManager` also removed `CameraManager`'s `PlacementManager` parameter/field entirely (arch flagged this as a required condition, not optional cleanup) — when a spec removes the *reason* two managers reference each other, grep for every consumer of the shared property before deciding the removal is complete, not just the one call site the spec names.
No live Unity/unity-mcp connection was available this session — verified by static/code review only (re-read every changed file, grepped for dangling references to removed members). Play Mode verification (placing/stacking/cascade-removing an actual container) is still outstanding and should happen before this is trusted as done.
**Apply when:** Any future placement-adjacent feature where a value (height, rotation, type) becomes *derived* rather than player-chosen — check whether the raycast/computation order needs to invert (know position before deriving the dependent value, vs. today's "know the value, then raycast at it"). Before closing out a dev pass with no Unity connection, say so explicitly in the completion report rather than implying Play Mode was checked.

### [2026-09-15] — Dev — #4 Conveyor Placement: GridManager as shared occupancy, combined placer+manager per arch guards, first live-MCP dev pass
**Context:** Built `GridManager` (arch condition 1), `ConveyorManager` (drag placement + belt movement + mutual exclusion with `PlacementManager`, arch condition 2), `GoodsData`/`GoodsAgent`, `ConveyorData`, and refactored `PlacementManager`/`Bootstrapper` to route occupancy through the new shared registry. First dev pass on this project with a live `unity-mcp` connection actually available.
**Learning:** `GridManager` ended up minimal by design — just `IsOccupied`/`Register`/`Unregister`/`NextFreeHeightLevel` over a `HashSet<Vector3Int>`. Each placer still keeps its own local `Dictionary<cell, GameObject>` for hit-testing/removal (unchanged from `PlacementManager`'s existing pattern) — `GridManager` only answers "is this cell taken," it doesn't own instances or do reverse lookups. This avoided a more invasive redesign and kept the diff to `PlacementManager` small (three call sites swapped from local `_occupiedCells` to `_gridManager`). Mutual exclusion between the two placement modes was implemented as reciprocal `ExitPlacementMode()` calls injected by `Bootstrapper` after both managers exist (can't inject at each manager's own creation time, since the *other* manager doesn't exist yet) — same shape as the #1→#2 `Camera.main` lesson: cross-manager references must respect `Bootstrapper.Awake()`'s actual creation order.
Deviated from the issue spec's suggestion of a separate `ConveyorPlacer` class: combined placement input and belt movement into one `ConveyorManager`, mirroring how `PlacementManager` already combines both roles for containers rather than introducing an asymmetric split. Documented as a deliberate choice, not an oversight — the resulting file is ~380 lines, over CLAUDE.md's ~150-line audit guideline (as `PlacementManager` itself already was, at ~300, without prior pushback), flagged here rather than split further since the spec itself scoped movement *into* `ConveyorManager`.
With a live Editor connection, verification went further than prior no-connection passes: entered Play Mode via `Unity_ManageEditor`, confirmed a clean console, and used `Unity_RunCommand` to directly call `GridManager.Register/IsOccupied/Unregister` at runtime as a functional smoke test of the shared-occupancy contract — this actually executes project code inside the running Editor, stronger evidence than reading the source. However, `Unity_RunCommand`'s dynamic-assembly sandbox threw an unexplained `NullReferenceException` on `System.Reflection` calls (`GetMethod`/`Invoke` against private methods) even wrapped in try/catch, before any of my own code ran — so simulated Tab/C keypresses (to verify the mode-exclusion integration end-to-end, not just via code review) weren't possible this session. No input-simulation MCP tool was available either. Actual drag-to-place, Q/R cycling, and Tab/C toggling remain manually unverified — flagged explicitly rather than implied as tested.
**Apply when:** Any future second (or later) placement system — reuse `GridManager` for occupancy, don't build a parallel registry. Any future cross-manager mutual-reference wiring — inject it from `Bootstrapper` after both sides exist, not from either manager's own `Initialize()`. If `Unity_RunCommand`-based reflection into private members proves unreliable again, don't sink time retrying it — fall back to testing through each class's actual public API, or note the verification gap plainly rather than working around the sandbox.

### [2026-09-16] — Dev — #4 follow-up: deck-level placement was burying pieces — pivot vs. mesh-center mismatch, only caught by the user's manual playtest
**Context:** User manually playtested #4 (per `/ux`'s own recommendation, since interactive input couldn't be simulated) and found placed conveyors sinking into the platform, centered inside the slab rather than resting on top.
**Learning:** `GridConfig` mapped height level 0 straight to world Y=0, but `SpacePlatformLargeBlue`'s mesh pivot sits at its own vertical center (`MeshRenderer.bounds` center ≈ transform position, size.y ≈ 1.384m) — confirmed by reading `bounds` on two separate instances via `Unity_ManageGameObject get_components`, not guessed. Fixed by adding `GridConfig.deckSurfaceHeight` (measured, not guessed — half the platform slab's height) and routing it through `Cell3DToWorld`/`WorldToCell3D`/`SnapPosition3D`, plus fixing the *same* Y=0 assumption in both placers' mouse-aim raycast planes (a second, less visible instance of the identical bug — aiming precision, not just the confirmed piece's resting height).
Verified the fix for real, not by re-reading code: temporarily instantiated a conveyor segment via `Cell3DToWorld` (the actual production method) at a cell over a real platform piece, then — since `Unity_Camera_Capture`'s default "Scene View" target didn't respond predictably to `SceneView.pivot`/`size`/`rotation` reassignment via `Unity_RunCommand` (repeated attempts left the platform out of frame for unclear reasons) — created a disposable `Camera` GameObject positioned/aimed explicitly via `Transform.LookAt`, and captured from that camera's instance ID instead. Cleaned up both temp objects afterward.
**Apply when:** Any future placeable-facing bug report — reach for `MeshRenderer.bounds` on the actual instances via `Unity_ManageGameObject`/`Unity_RunCommand` to measure the real geometry rather than assuming a prefab's pivot is at its base. When `Unity_Camera_Capture`'s default SceneView target won't frame reliably via `SceneView` property assignment, spawn a disposable `Camera` GameObject and capture by instance ID instead — more predictable, same cleanup discipline as any other temp verification object. ### [2026-09-16] — Dev — #6 Receiving Dock: hit the Bootstrapper AddComponent/Initialize ordering bug myself, then discovered Play Mode was frozen the whole time
**Context:** Built `ReceivingManager`/`ReceivingDock`/`ReceivingData`, plus the two arch-required changes (GridManager registration for the fixed dock, ConveyorManager's `RegisterGoodsAgent`/public `SegmentWorldPosition`).
**Learning:** Two real findings, one code bug and one environment bug, each worth its own entry.
1. **Code bug:** Put the dock-registration logic in `ReceivingManager.Awake()`, gated on `_gridConfig`/`_gridManager` being non-null. First Play Mode test showed the dock's cell as *not* occupied despite the code clearly running. Root cause: exactly the pitfall `DECISIONS.md`'s #2 entry already documented for `Camera.main` — `Bootstrapper.CreateReceivingManager()` uses `AddComponent<ReceivingManager>()`, which fires `Awake()` **synchronously before** the subsequent `Initialize(...)` call sets those fields, so the null-check silently no-op'd. Fixed by moving all of the setup (dock-finding *and* registration) into `Initialize()` itself, matching how `PlacementManager`/`ConveyorManager`/`CameraManager` already only do injected-data-dependent work there, never in `Awake()`. A documented decision in memory didn't prevent a fresh instance of the exact same bug — it has to be checked against *every* new `Bootstrapper`-created manager, not just remembered in the abstract.
2. **Environment bug (much bigger, project-wide):** After the fix compiled clean, `Time.time` stayed at `0` and no goods ever spawned even after real wall-clock waits. Root cause: `Application.runInBackground` / `PlayerSettings.runInBackground` was `false` — Unity freezes Play Mode's entire frame loop at frame 0 whenever the Editor window isn't OS-focused, which is *always* true for an MCP-driven session (nothing ever clicks into the window). `Unity_RunCommand` calls kept succeeding and returning real data throughout, because they run on the Editor's own update, not the frozen Play Mode player loop — so a stalled Play Mode is easy to mistake for "hasn't happened yet" rather than "will never happen." This retroactively explains #4's `/ux` review being unable to get `InputSystem.QueueStateEvent`-simulated input to register (logged there as an "unclear timing issue" — it wasn't timing, it was a fully frozen loop). Fixed by setting `PlayerSettings.runInBackground = true` **while in Edit mode** (setting it during Play Mode itself didn't persist — reverted to `false` on Stop) and confirmed written to `ProjectSettings/ProjectSettings.asset` on disk.
Once fixed, real interactive verification worked end-to-end for the first time this project: `InputSystem.QueueStateEvent` (not reflection — that sandbox limitation from #4 still stands) simulated C (toggle conveyor mode), a full mouse drag (press/move/release) to place two segments, Q to cycle flow direction, and right-click removal — each queued in a *separate* `Unity_RunCommand` call with a real `Bash sleep` between them, since Play Mode only advances between calls, not within one (confirmed: looping `Thread.Sleep`+`EditorApplication.QueuePlayerLoopUpdate()` *inside* one call does not work — it blocks the same main thread the player loop needs). Watched a `GoodsAgent` move cell-to-cell in real time on a correctly-flowing belt (`(4, 0.99, 8)` → `(4, 0.99, 4)` over ~3s at `beltSpeed=2`, matching the math exactly) — first time this project has verified gameplay behavior by actually driving it rather than reading code or checking bookkeeping state.
**Apply when:** Any future `Bootstrapper`-created manager whose `Initialize()` does real setup work — put that work in `Initialize()`, never `Awake()`, full stop; don't re-derive this from first principles each time. Before starting any session that needs Play Mode verification, check `PlayerSettings.runInBackground` first (`grep runInBackground ProjectSettings/ProjectSettings.asset` needs `: 1`) — if a future regression sets it back to `false`, every subsequent timer/input-simulation test will silently fail in a way that looks like "nothing happening yet." Interactive input simulation via `InputSystem.QueueStateEvent` is now a real, reliable verification tool for this project — spread each discrete input transition across its own `Unity_RunCommand` call with a real-time wait between, compute screen positions via `Camera.main.WorldToScreenPoint(gridConfig.Cell3DToWorld(cell))`, and remember drag flow direction (Q/R) is independent of drag direction — don't forget to set it before releasing, or the placed segment won't lead anywhere the good can reach.

### [2026-09-16] — Dev — #6 retry: AdvanceGoods needed per-cell collision awareness, not just per-cell segment awareness
**Context:** `/ux` FAIL on #6's first pass — driving the dock's real timer against a short dead-end belt produced 5 `GoodsAgent`s fully overlapping at the same world position instead of queuing, discovered only because interactive Play Mode verification (newly working, see above) let continuous multi-spawn behavior actually run instead of being reasoned about statically.
**Learning:** `AdvanceGoods` (from #4) only ever checked whether the *target cell* had a registered conveyor segment before moving an agent onto it — never whether another `GoodsAgent` was already sitting there. Fixed with a linear `IsCellOccupiedByOtherAgent(cell, excluding)` scan over `_activeGoods` (same "fine at Phase 1 scale" tradeoff already used by `GridManager.NextFreeHeightLevel`), called before the move each frame. This composes correctly with `ReceivingManager`'s existing "skip spawn if last-spawned agent still at output cell" check with no changes needed there: once an agent is blocked from advancing, it sits at its own cell, and if that's the dock's output cell, the dock's own backpressure check naturally stops further spawns too. Verified by replaying the exact scenario that broke: same dock, same belt, same ~10s wait — count went from 5 overlapping agents to 2 correctly queued ones (one per cell, up to the dead end).
**Apply when:** Any per-frame movement system where multiple independent agents can target the same destination — check occupancy by *other agents*, not just by static world/segment state, or a busy system will silently overlap instead of visibly queuing. This gap couldn't have been caught by the queuing-agnostic occupancy tests run during #4's original dev pass (they only checked segment/grid bookkeeping, never multiple simultaneously-active goods) — a second reminder that visual/interactive verification catches a category of bug that data-structure smoke tests structurally cannot.

### [2026-09-16] — Dev — Flow-direction arrow: procedural mesh + shared URP Unlit material, parented with identity rotation to reuse the parent's own direction math
**Context:** Direct request (no issue) — player couldn't tell which way placed conveyors flow, since `TurretPlatformFlyingBlue`'s placeholder visual reads as symmetric even when correctly rotated by `FlowRotation()`.
**Learning:** Built a small flat 2-triangle arrow as a runtime `Mesh` (6 vertices/2 tris, no imported asset — `CreatePrimitive` has no cone/arrow `PrimitiveType`, so a hand-built mesh was simpler than compositing primitives) tinted via a `Material(Shader.Find("Universal Render Pipeline/Unlit"))` (URP-only per CLAUDE.md convention; Unlit specifically so the indicator reads at a consistent brightness regardless of scene lighting). Both the mesh and material are built once (lazily cached on first use, `_flowArrowMesh`/`_flowArrowMaterial` instance fields) and shared by reference across every segment's arrow child — cheap, no per-segment allocation. The arrow GameObject is parented with `localRotation = Quaternion.identity`, so it inherits the segment's own `FlowRotation()`-applied world rotation automatically — no separate direction computation needed, and no risk of the two ever drifting out of sync. Measured the placeholder prefab's own `MeshRenderer.bounds`/`MeshFilter.sharedMesh.bounds` first (top surface at local Y=0.32) to place the arrow at Y=0.4, clearing the mesh rather than clipping into it — same "measure, don't guess" lesson as the earlier deck-height bug. Applied to both ghost preview and confirmed instances; inserted the preview call *after* the existing valid/invalid tint loop (`GetComponentsInChildren<Renderer>` at that point doesn't yet include the arrow), so the arrow keeps its own fixed amber color regardless of preview validity — direction stays readable even on an invalid (red) preview. Needs no explicit cleanup — as a child object it's destroyed automatically whenever its parent segment is (`Destroy(_segmentInstances[cell])` on removal, or preview teardown) — confirmed via a live removal test (arrow count matched remaining segment count exactly).
**Apply when:** Any future placeholder-art gap where a direction/state needs to be visually communicated but no real asset exists yet — a cheap procedural `Mesh` + shared `Unlit` material, parented with identity local rotation onto whatever object already carries the relevant rotation, avoids both new asset imports and duplicated direction math. Before offsetting a child indicator above a placeholder mesh, measure that mesh's actual bounds rather than guessing a Y offset.

### [2026-09-16] — Dev — Goods now ride visibly on top of conveyor segments — separate GoodsRestPosition from SegmentWorldPosition, don't reuse one height for two different things
**Context:** Direct follow-up request right after the flow-arrow fix — the UX review earlier in this project had already flagged (as a non-blocking placeholder-art note) that goods and segments sharing the exact same `SegmentWorldPosition` height meant a good was nearly swallowed under the much-larger segment mesh. The user asked for it directly this time: goods should visibly ride on top.
**Learning:** The fix was to stop treating "segment height" and "goods height" as the same number. Measured both prefabs' bounds first rather than guessing: `TurretPlatformFlyingBlue`'s top surface sits at local Y=0.32 (already known from the earlier deck-height fix), and `Pallet1`'s own pivot turned out to already be at its base (bounds center Y=0.09, extent Y=0.09 → spans 0 to 0.18) — no separate pivot correction needed for the goods prefab itself. Added `ConveyorData.goodsRideHeight` (default 0.32, matching the segment's measured top surface exactly) and a new public `ConveyorManager.GoodsRestPosition(cell) = SegmentWorldPosition(cell) + up * goodsRideHeight`, then swapped every goods-positioning call site (`AdvanceGoods`'s movement target, `SpawnDebugGoods`, and `ReceivingManager`'s spawn) from `SegmentWorldPosition` to `GoodsRestPosition` — segment placement itself (`RebuildPreview`/`ConfirmDrag`) still correctly uses `SegmentWorldPosition` unchanged, since only goods needed to move up. This is the same "measure, don't guess" and "separate the reusable public method per actual use-case rather than overloading one" pattern as the earlier `deckSurfaceHeight` fix — a shared height getter tempts every caller into reusing it even when their actual needs differ (segment resting height vs. goods riding height are conceptually different things that happened to start out equal).
**Apply when:** Whenever two different kinds of objects share a hover/rest-height getter "for now" because their values happen to coincide — watch for the moment their needs diverge (here: readability required goods to sit *above* segments, not level with them) and split the getter rather than special-casing call sites. Always measure a placeholder prefab's actual `MeshRenderer.bounds`/`MeshFilter.sharedMesh.bounds` before picking an offset that positions something relative to it.

### [2026-09-16] — Dev — #5 Type-Locked Storage: marker component to disambiguate a shared event, reverse-iterate for mid-loop removal, Animator.Play by name with no parameters
**Context:** Built `StorageManager`/`ContainerInstance`/`ContainerData.capacity` plus the two arch-required fixes: a way for `StorageManager` to tell a container placement apart from a conveyor placement on the shared `PlacementEventChannel`, and the actual `ConveyorManager` → `StorageManager` goods handoff that didn't exist before this issue.
**Learning:** Solved the event-channel ambiguity with the simplest thing that works — `PlacementManager.TryConfirmPlacement` attaches a `ContainerInstance` component (`AddComponent`, not part of the prefab) right after instantiating, and `StorageManager.HandlePiecePlaced` just checks `TryGetComponent<ContainerInstance>` on the incoming instance; present means container, absent (e.g. a conveyor segment, which raises the identical event) means ignore. No new event channel, no payload changes, no reflection — just a marker component doing exactly what marker components are for. `ConveyorManager.AdvanceGoods` needed converting from `foreach` to a reverse `for` loop (`i = _activeGoods.Count - 1; i >= 0; i--`) so a successful hand-off could `RemoveAt(i)` mid-iteration without the usual "collection was modified" exception — same shape as any other safe-removal-during-iteration pattern, just the first time this project needed it.
`HangarBlue`'s shipped `HangarGrey` AnimatorController has real states (`HangarClosed`/`HangarOpened`/`HangarOpen`/`HangarClose`) but zero exposed parameters and zero auto-transitions between states — confirmed via `AnimatorController.parameters`/`state.transitions` before writing any animation code, not assumed. So `ContainerInstance` drives it with plain `Animator.Play("HangarOpen")`/`Play("HangarClose")` (state name, not `SetBool`/`SetTrigger`) — each clip just plays once and holds its last frame, which already looks like the intended `Opened`/`Closed` held state with no chaining needed. Its actual default state (`HangarOpenCloseDEMO`, a demo loop) had to be explicitly overridden to `HangarClosed` in `Initialize()` — left alone, every fresh container would loop a demo animation forever. The ghost preview needed the same override but chose `previewAnimator.enabled = false` instead of hardcoding a state name into the more-generic `PlacementManager`, since a preview shouldn't animate at all regardless of which container type it's for.
Verified live, not just by reading code: placed a real Hangar, connected a conveyor into it, debug-spawned a good, and watched it get absorbed — `ContainerInstance.LockedType`/`CurrentCount` confirmed correct, and a repositioned temp camera caught the door genuinely mid-open (lit interior visible). Capacity/rejection edge cases were **not** independently live-verified this pass — mid-session, `Mouse.current.position` started resetting to `(0,0)` on every natural frame no matter how many times it was re-queued (even survived a manual `InputSystem.Update()` flush in the same call), first noticed right after several `Unity_Camera_Capture` calls in a row; never diagnosed further, just worked around by relying on the one live success plus code review of `TryAccept`'s straightforward boolean logic for the untested paths.
**Apply when:** Any future case where two different placement kinds share one event channel — reach for a marker component on the instance before inventing a richer event payload or a second channel.
