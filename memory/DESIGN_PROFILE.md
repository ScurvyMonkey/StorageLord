# Design Profile

How this designer communicates, what they value, how they make decisions — logged by `/ba`.

### [2026-09-15] — BA — Genre references describe the goal, not a literal mechanic to copy; converges fast on Recommended when forks are flagged clearly
**Context:** First real spec pass (#1, Runtime Grid Placement). The ask cited "stacking in Satisfactory" as the reference for wanting height/verticality in the grid.
**Learning:** Read literally, Satisfactory's verticality comes from foundation-based multi-story building (support required below), not freeform floating placement. Rather than assume the literal mechanic, surfaced it as an explicit fork (freeform vs. requires-support-below) via a 2-question `AskUserQuestion` batch alongside a second real fork (whether to also extend the Editor-time platform tool). Both answered with the Recommended option in one pass, no deliberation — the Satisfactory mention was about the *outcome* they want (compact vertical storage, not flat sprawl), not a request to build support/foundation logic.
**Apply when:** When a request cites another game as a reference point, treat it as describing the feeling/outcome they want, not a spec for that game's literal systems — if the literal mechanic would meaningfully change scope or architecture, surface it as an explicit question rather than assuming either the literal or the simplified reading. This designer converges quickly on a clearly-labeled Recommended option once the fork is visible, even across multiple bundled questions.

### [2026-09-14] — BA — Multiple cited games can itself be the ambiguity; picks the option matching existing project signals over the genre default
**Context:** Camera system ask (#2) cited "Shapez or Shapez 2" together, as if interchangeable. They aren't — Shapez 1 is locked top-down orthographic, Shapez 2 is free-orbit perspective. Also relevant: GDD's own Open Questions note said genre precedent points toward top-down/isometric, which would have argued for the "simpler" reading.
**Learning:** When a request names two+ games as one reference, don't assume they're equivalent — check whether they actually differ on the axis that matters and surface that as the fork. This designer picked the option that matched an existing but easy-to-miss project signal (`CLAUDE.md`'s Unity MCP note that this is "a 3D project, not 2D top-down like other projects") over the GDD's own stated genre-precedent lean toward top-down/isometric — i.e., they weight concrete project-specific signals over general genre-default reasoning.
**Apply when:** A request cites multiple games/references together — verify they actually agree before treating them as one reading. When surfacing the fork, check `CLAUDE.md`/GDD for any existing signal (even an offhand one) that already leans toward an answer, and don't let a stated "genre precedent" note override a more specific project signal when framing the Recommended option.

### [2026-09-15] — BA — Will reverse an earlier "Recommended, agreed" decision once they've actually played it; doesn't default to Recommended when a bundled action changes what a single click does
**Context:** #1's fork picked "freeform" placement (the Recommended option at the time) over "requires support below." After playing the freeform version and hitting an unrelated placement bug, the designer came back unprompted and asked for support-required auto-stacking — the exact mechanic freeform had been chosen over. Separately, in that same follow-up spec (#3), a 3-option fork asked what happens removing a container with something stacked on top: they picked "cascade-remove the whole stack" over the Recommended "block the removal," while still picking Recommended on the other two forks in the same spec (support-detection method, stack cap).
**Learning:** A "Recommended, agreed" choice from an earlier spec is not a settled preference — it's provisional until played. Don't treat prior spec decisions as closed; if the user reopens one, that's them acting on real play experience, not indecision, and it deserves the same full fork treatment as a first-time ask. Also: this designer doesn't rubber-stamp Recommended across a bundled question set — they pick per-question based on what feels right for that specific interaction, and readily go with the *more permissive/less restrictive* option (cascade-remove, a bigger single action) over the *safer/more conservative* one (block removal) when the safer option would make a common interaction (clearing a stack) more tedious.
**Apply when:** Never assume an old spec decision is final just because it was agreed to and shipped — if the user's later request would functionally reverse it, treat it as a real re-fork, not a bug report. When a bundled `AskUserQuestion` includes both a "safe/blocking" and a "permissive/bulk-action" option, don't assume Recommended (often the safe one) is the likely pick — this designer weighs player convenience for common actions over defensive restriction.

### [2026-09-15] — BA — Names multiple assets/references for one role without specifying which does what; self-flags when they've likely over-scoped
**Context:** Conveyor + storage ask named two placeholder assets ("flying platforms... or Pallets+Container") for one stated role ("our floating conveyor system") without saying which was which — same shape as the earlier Shapez/Shapez 2 ambiguity (#2), but for art assets instead of games. Separately, the user opened the request by saying "I think I may have jumped ahead too far" about the previous session's direct-placement work, unprompted.
**Learning:** This designer's habit of naming multiple references together for one slot isn't limited to genre/game citations — it recurs with placeholder art too, and the resolution is the same: split the compound reference into distinct roles and ask, rather than picking one. Also confirmed: they self-audit sequencing/scope without being asked (volunteering "jumped ahead" rather than needing it pointed out), so when a `/ba` pass finds the same kind of gap independently, it lands as confirmation of something they already suspected, not unwelcome pushback.
**Apply when:** Any time a request lists 2+ named things (games, assets, prefabs, references) for what's described as a single role, treat it as an unresolved fork worth asking about, not a preference to guess at. When the user opens a request with self-doubt about scope/sequencing, a `/ba` pass that independently flags a real gap (missing prerequisite system, phase-scope creep) will land well — don't soften or skip that flag to avoid seeming to pile on.

### [2026-09-17] — BA — Picks the richer/more-complex option over Recommended when their own narrative already implied it, even against a "simpler is safer" framing
**Context:** #9 (Shipping Docks & Company Orders) bundled 4 forks; 3 of 4 went with Recommended, but "order concurrency" (one active order at a time vs. multiple simultaneous) went the *other* way — multiple concurrent orders, against the Recommended single-order model, even though the Recommended option was framed as matching the user's own "first event... next event" phrasing and being the simpler data model.
**Learning:** This designer's earlier-logged tendency to pick the more permissive option over the safer one (see #1/#3 entry above) extends to a different axis here: system *richness/complexity*, not just player-convenience/safety. Their own narrative ("the Company... different requests will come in from various places") already implied real parallelism, and they picked the option that honored that implied richness over the one that read as simpler-to-build-and-reason-about — even though the Recommended framing quoted their own words back at them as support for the simpler choice. A Recommended label built on "this matches what you said" isn't a safe bet if a *different* part of the same request implies more complexity than the literal phrasing suggests.
**Apply when:** When multiple parts of one request pull in different directions (a simple example alongside language implying a richer system), don't resolve the tension by picking whichever reading is simpler and calling it Recommended — surface the real tension in the question itself, or expect the richer reading to win. Don't assume a designer who just picked Recommended on 3 out of 4 questions in a batch will keep doing so on the 4th; each fork gets evaluated on its own terms.

### [2026-09-18] — BA — A game-reference citation can arrive pre-disambiguated; the genre precedent narrows the fork instead of creating one
**Context:** The ask for anchor-and-stretch conveyor placement cited "Satisfactory or other factory style games" — same shape as the earlier Shapez/Shapez 2 citation (#2) that needed forking — but this time came bundled with a full mechanical description upfront (click to anchor, drag to a capped max distance, release to place). Only one real fork remained (does the dragged-to end also get a platform, or just the clicked end) — asked as a single focused `AskUserQuestion`, picked Recommended (platform at both ends) without hesitation.
**Learning:** Not every genre citation is an ambiguity to resolve from scratch — check whether the ask already supplies enough mechanical detail to narrow the reference to one reading before treating it as a fork the way #2's bare "Shapez or Shapez 2" needed. This designer volunteers real mechanical detail unprompted when they've already thought the feature through (this wasn't a vague "make it like Satisfactory," it was a specific description that happened to cite Satisfactory as shorthand for the feel) — the remaining fork was narrow and specific (one structural detail: platform count at the far end), not "which game did you mean."
**Apply when:** When a request cites a game reference alongside a concrete mechanical description, trust the description over the citation and look for the *specific* remaining gaps rather than re-litigating whether the genre reference itself is ambiguous — the citation is doing less work than it did in the #2 case, where it was the *only* information given.

### [2026-09-20] — BA — Blanket "you have my approval, go forth" doesn't mean skip the questions — it means the designer trusts the process to move fast once scope is clear
**Context:** User granted open-ended 24-hour approval and asked to "finish Storage Lord" with a large, vague, multi-system ask (random map generator, 60x60 scale, undefined "events," a loss condition) in one enthusiastic message. Rather than take the blanket approval as license to skip clarification and start building, presented three sharp forking questions with a labeled "Recommended" (lower-risk) option on each.
**Learning:** The designer accepted every Recommended option immediately, with zero pushback on the fact that this de-scoped "random map generator" down to "one hand-curated large layout" and "events" down to "escalating order waves" — both meaningfully smaller than what the original message literally asked for. This confirms (extending the #2/#10 pattern already logged) that this designer's enthusiasm/urgency in a request is not a signal to skip scoping — it's trust that the assistant will ask the *right*, *minimal* set of questions and then actually move, not a request to bypass judgment. Big, hyped asks from this designer ("go forth and conquer," blanket approval) should be met with the same decomposition discipline as any other request, just delivered fast and without excess hedging.
**Apply when:** A request carrying explicit "you have my approval" / "just go do it" language is not itself information about desired scope — treat it as permission to move quickly through the pipeline (spec → arch → dev in one sitting, autonomous `/handoff` chaining) once scope is actually resolved, not as permission to skip the scoping step itself. Default to offering a clearly-labeled lower-risk "Recommended" option on any genuinely open fork even under time pressure — this designer takes it every time it's offered.
