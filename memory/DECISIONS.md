# Decisions

Architecture/design decisions logged by `/arch`.

### [2026-09-15] — Arch — #1 Runtime Grid Placement: extend GridConfig additively, event channel required, Bootstrapper stays minimal
**Context:** First architecture review on the project. #1 adds height/3D placement to the existing (X/Z-only) `GridConfig` and introduces the project's first real runtime manager (`PlacementManager`, via a new `Bootstrapper`).
**Learning:** Verified against the actual `GridConfig.cs` source (not just the spec's claim) that the planned extension is genuinely additive — new `cellHeight` field plus distinctly-named `Vector3Int` methods (`WorldToCell3D`/`Cell3DToWorld`), no overloads colliding with the existing `Vector2Int` API the Editor tool depends on. Also caught that CLAUDE.md's own Event-Driven Communication table already names "placement confirmed" as a ScriptableObject-event-channel case — the issue spec didn't include one, which is a real convention gap, not a nice-to-have I invented. Flagged it as a condition rather than blocking on it, since it's cheap to add now and expensive to retrofit once `StorageManager` needs to react to placement later.
**Apply when:** When a spec is the *first* implementation of a manager/pattern that CLAUDE.md only proposes, check the proposal against real code before either approving or citing it as a violation — a proposal doc can be stale in either direction. When a new system creates the project's first `Bootstrapper`/manager, watch for scope bleed into stubbing out other proposed managers (`GameManager`, `UIManager`, etc.) that aren't part of the actual spec — flag that as a guard even if the spec itself doesn't mention doing it, since "while I'm in there" is a natural temptation on a from-scratch file.

### [2026-09-14] — Arch — #2 Free-Orbit Camera: Camera.main must stay scene-pre-placed; Bootstrapper.AddComponent runs Awake synchronously
**Context:** #2 added a `CameraManager`, and its own spec left "who owns the scene's `Camera.main`" as an open question for `/dev` to decide.
**Learning:** That's not actually a free choice — `PlacementManager.Awake()` caches `Camera.main` once and never re-queries it, and `Bootstrapper.CreatePlacementManager()` uses `AddComponent<PlacementManager>()`, which fires that `Awake()` **synchronously, inline**, during `Bootstrapper.Awake()` — not deferred to next frame like a naive reading of "Unity calls Awake before the first Update" might suggest. If any Bootstrapper-created manager created *after* `PlacementManager` in `Awake()` replaces/reparents/destroys the `MainCamera`-tagged camera, `PlacementManager`'s cached reference goes stale with **no error** (its null-checks just silently no-op). Any future manager touching the scene's main camera must either run its camera setup *before* `CreatePlacementManager()` in `Bootstrapper.Awake()`, or (safer) never destroy/recreate the camera at all — just reposition the existing one.
**Apply when:** Any future spec involving the `Camera`/`Camera.main` (camera rigs, split-screen, cutscene cameras) — check `PlacementManager`'s (and any later system's) `Awake`-time camera caching before treating camera ownership as an open implementation detail. More generally: `Bootstrapper`'s `AddComponent<T>()` pattern means manager creation order in `Bootstrapper.Awake()` is a real dependency graph, not just a list — a manager that needs another manager's `Awake()` to have already run must be created after it.

### [2026-09-15] — Arch — #3 Support-Required Auto-Stack Placement: removing a system's input usage must also remove the coupling it justified, not just the behavior
**Context:** #3 removes `PlacementManager`'s scroll-driven height control, which was the entire reason `CameraManager.HandleZoomInput()` checks `IsPlacementModeActive` and the entire reason `CameraManager` holds a `PlacementManager` reference at all (per `Bootstrapper`'s own doc comment on creation order).
**Learning:** The issue spec only stated the visible behavior change ("zoom works during placement now"), not the structural cleanup that behavior change implies. Flagged as a condition: when a spec removes *why* two systems were coupled, the coupling itself (injected reference, constructor parameter, exposed property, doc comments justifying creation order) must be removed or re-justified in the same pass — otherwise it becomes exactly the "half-finished" dangling state `CLAUDE.md`'s style section warns against, just at the architecture level instead of the code-comment level.
**Apply when:** Any future spec that removes or repurposes the reason two managers reference each other (not just removes a line of behavior) — check every consumer of the shared reference/property, not just the one the spec explicitly mentions, before approving as a clean removal.

### [2026-09-15] — Arch — #4 Conveyor Placement: a second independent placer class needs a shared occupancy authority, not two private registries
**Context:** #4 introduces the project's first *second* runtime placement class (a conveyor placer, separate from `PlacementManager` since drag-based input differs enough from single-click to warrant its own class per SRP). Neither the spec nor the existing code gives the two placers any shared way to know what the other has occupied.
**Learning:** `PlacementManager._occupiedCells`/`_placedPieces` are private to that one `MonoBehaviour` — there's no queryable occupancy authority elsewhere in the project. Two independent placers can each confirm a piece into a cell the other already occupies, which is a direct violation of the "live validity, never confirm what a later frame could reject" contract and results in literal geometry overlap (Pillar 3 violation). This is the exact scenario CLAUDE.md's Proposed Manager Hierarchy already named as the trigger to revisit `GridManager`'s necessity ("revisit once ConveyorManager needs shared occupancy state across systems") — flagged as a required condition rather than a nice-to-have, since a real `GridManager` is cheap to add now and expensive to retrofit once both placers have shipped against their own private state.
**Apply when:** Any future spec that adds a second (or later) independently-input-driven placement class — always check whether it shares an occupancy registry with every other placer before approving, don't assume separate classes imply separate/independent state is fine. This is also the trigger point CLAUDE.md itself predicted for building `GridManager` for real — future specs shouldn't need to re-discover this, just build it once here.

### [2026-09-16] — Arch — #6 Receiving Dock: fixed/static pieces must register with GridManager too, not just runtime placers
**Context:** #6 introduces the project's first fixed, Editor-placed *gameplay* piece that isn't going through `PlacementManager`/`ConveyorManager` at all (deliberately, per the GDD's "fixed dock" language) — but the spec never registered its footprint with `GridManager`.
**Learning:** #4's shared-occupancy fix only closed the gap *between* the two runtime placers; it didn't establish that *every* piece occupying a cell — including ones placed outside either runtime placement flow — must register with `GridManager`. A fixed dock sitting outside that registry is invisible to both placers' live-validity checks, so a player can confirm a container/conveyor directly on top of it. Flagged as a required condition (register the dock's footprint at startup) rather than optional, same bar as #4's condition.
**Apply when:** Any future piece that occupies grid space but isn't placed through `PlacementManager` or `ConveyorManager` (future Shipping docks, any other Editor-authored fixture) — it still needs to register its footprint cell(s) with `GridManager` at scene-start, or runtime placement can silently overlap it. "Goes through the shared occupancy registry" applies to anything occupying a cell, not just to the two systems that happen to fight over it today.

### [2026-09-16] — Arch — #5 Type-Locked Storage: a spec written before #4/#6 landed missed two integration points that now genuinely don't exist
**Context:** #5 (Type-Locked Storage Containers) was spec'd via `/ba` before #4 (conveyors) and #6 (Receiving) were implemented. Its own acceptance criteria describe a conveyor→container goods handoff and a `PlacementEventChannel` subscription that, read against the actual shipped code, don't work.
**Learning:** `PlacementEventChannel.OnPiecePlaced` is raised by *both* `PlacementManager` (containers) and `ConveyorManager` (conveyor segments) on the same shared channel instance, with no kind discriminator in its `Action<GameObject, Vector3Int>` signature — a naive `StorageManager` subscriber can't tell a container placement from a conveyor placement. Separately, `ConveyorManager.AdvanceGoods` only ever checks whether a `GoodsAgent`'s next cell is a registered *conveyor segment* — if it's a container instead, the agent just holds forever with no attempt to hand off. Neither gap could have been caught when #5 was originally spec'd, since neither `ConveyorManager`'s final shape nor the shared-event-channel reuse existed yet at that point. Flagged both as required conditions: a container-identifying marker component (so the event channel becomes filterable) and a new `ConveyorManager`→`StorageManager` reference (Bootstrapper-injected after both exist, same pattern as `ReceivingManager`→`ConveyorManager`) for the actual handoff logic.
**Apply when:** Any spec whose implementation was deferred long enough that *other* systems it depends on shipped in the meantime — re-verify its stated integration points against the actual current code, not just the spec's own text, before treating "Affected Systems" as complete. A cross-system handoff (goods moving from one manager's domain into another's) is exactly the kind of thing a spec can describe in prose without anyone noticing the actual code path doesn't exist yet.

### [2026-09-17] — Arch — #7 Conveyor Networks: a feature that first uses an existing axis meaningfully can break an invariant that only ever held by accident
**Context:** #7 (Junctions, Backflow Prevention, Multi-Level Stacking) is the first spec to give conveyors a real Y-axis — previously deck-level-only. `GridManager.NextFreeHeightLevel` (used only by `PlacementManager` for container auto-stack, confirmed via a single-call-site grep) computes `max(occupied.y) + 1` over a column, which has always been equivalent to "first free level from 0" purely because containers are the only thing that has ever used the Y axis, and containers always stack contiguously from the bottom by construction (`PATTERNS.md`'s #3 entry names this exact invariant).
**Learning:** An invariant that's actually "only true because nothing has ever exercised the axis differently yet" reads as settled/safe until a new spec is the first to violate the *unstated* half of it. Here: a conveyor floating at height 1 with height 0 left empty (the literal point of "fly a belt over an obstacle") makes `NextFreeHeightLevel` return 2 instead of 0, silently blocking container placement at a genuinely free deck cell — a first-use regression, not an edge case, and not something #4/#5/#6's own dev passes could have caught since conveyors never touched Y before now. Verified the fix (walk Y from 0, return first unoccupied) is backward-compatible for every existing (contiguous-only) caller before flagging it as a required condition rather than a nice-to-have.
**Apply when:** Any future spec that's the *first* to exercise an existing shared data structure (occupancy, event channel, dictionary) along a dimension/pattern it was never exercised along before — re-derive whether every downstream consumer's assumption about that structure was actually enforced by the code, or just happened to hold because nothing tested the other case yet. Grep every call site of the shared method/structure being newly stressed, don't just check whether the new spec's own feature works in isolation.

### [2026-09-18] — Arch — #10 Anchor-and-Stretch Conveyor Placement: a visual-only rework can still break correctness if a shared GameObject replaces what used to be one-GameObject-per-cell
**Context:** #10 replaces per-cell platform instantiation with anchor platforms + fill pieces, explicitly scoped as visual/placement-UX only (no change to goods movement, junctions, or backflow, all of which stay keyed off `_segmentFlowDirections` per-cell exactly as today).
**Learning:** `ConveyorManager`'s removal (`HandleRemoveInput`) and debug-spawn (`HandleDebugSpawnInput`) both raycast-hit-test against `_segmentInstances`, a `Dictionary<Vector3Int, GameObject>` built on the assumption that every cell owns an *independent* `GameObject` — true today (one platform prefab per cell), but not automatically true once a single `BeltSystem` fill piece can represent multiple cells' worth of visual space. Removing one cell under that assumption calls `Destroy()` on a `GameObject` other cells' dictionary entries still reference, producing dangling references and orphaned occupancy — a genuine correctness bug, not a style concern, and one the spec's own Open Questions gestured at (removal granularity) without fully resolving. Condition: removal must operate on the whole anchor-to-anchor span (not per-cell), and a new per-span tracking structure is needed rather than forcing the grouping into `_segmentInstances`'s existing one-GameObject-per-cell shape. Separately, direct inspection of the actual `BeltPlatform`/`BeltSystem` prefabs (not the spec's prose description) resolved the spec's other open question: `BeltSystem`'s natural length already matches one grid cell's gap, with fixed-offset end-cap meshes that would distort under non-uniform scaling — so it tiles as fixed-length units, it doesn't stretch arbitrarily.
**Apply when:** Any future spec that changes *which* `GameObject` gets instantiated per grid cell, even when framed as "visual only" — check every existing raycast-hit-test/removal code path that assumes a 1:1 cell-to-`GameObject` relationship before approving, since a shared visual object across multiple cells breaks that assumption silently. When a spec's own Open Questions include a technical feasibility fork about an asset already built by the designer, inspect the actual prefab (hierarchy, mesh bounds, fixed vs. relative child offsets) rather than resolving it from the spec's prose — the asset itself usually already answers the question.

### [2026-09-20] — Arch — #11 Large Platform Layout: camera pan bounds don't auto-scale with platform size, and neither does anything else tunable
**Context:** #11 scales the platform from its current small footprint to ~60x60m, framed by its own spec as "no runtime code changes expected" (pure content, existing Editor tool).
**Learning:** `CameraConfig.panBoundsRadius` (40m) is a fixed data value with no relationship to actual platform extent — a 60x60m platform's corners (~42.4m from origin) sit outside it, meaning the player literally cannot pan the camera far enough to see the very platform this issue builds. This is still consistent with "no runtime code changes" (it's an asset value, not a script change) but would have shipped as a real, immediately-noticeable bug if not caught here — the spec's own "no code changes" framing made it easy to assume nothing needed touching at all.
**Apply when:** Any future spec that changes world-space scale (bigger platform, moved docks, a second area) must be checked against every *tunable value* that implicitly assumed the old scale, not just against code paths — `CameraConfig`'s pan/zoom bounds are the obvious one here, but the same category of gap could hit anything with a hardcoded distance/radius tuned against "how big the platform used to be."

### [2026-09-20] — Arch — #12 Run Loss Condition: a spec describing an end-state didn't audit whether the systems it needs to halt can actually be halted
**Context:** #12 (first real `GameManager`, run ends at N missed orders) states in its own Gameplay Behavior section that placement, conveyor movement, and spawning must all stop at game-over, but its Affected Systems list only names new files.
**Learning:** Checked all four systems the spec implicitly depends on (`ConveyorManager`, `PlacementManager`, `ReceivingManager`, `ShippingManager`) directly — none expose any external stop/disable surface today; every one of their `Update()` methods runs unconditionally. This is the same category of gap `DECISIONS.md`'s #5 entry logged (a spec's stated integration points not actually existing in code), except here it's not a timing/staleness issue — it's that "and then everything stops" reads as a simple sentence in a spec but corresponds to zero existing hooks in four separate files.
**Apply when:** Any future spec describing a global state change ("the game stops," "everything pauses," "the run ends") — explicitly enumerate every system that state change needs to reach into and verify each one already has (or the spec adds) a way to be told about it, rather than treating "and X stops" as self-evidently already possible. A `GameManager`/run-state system is exactly where this risk concentrates, since by nature it needs to reach across most of the codebase.

### [2026-09-20] — Arch — #13 Escalating Order Waves: reusing an existing data flow is easy to verify structurally, but "reuse the existing pool" can describe a pool that doesn't exist yet
**Context:** #13 generates `OrderData` at runtime once the authored schedule is exhausted, stated as reusing "the existing GoodsData pool."
**Learning:** Traced the actual data flow (`ActiveOrder` only reads post-construction fields, `ShippingScheduleData` is just an `OrderData[]`, `ShippingManager` holds no `GoodsData` reference anywhere) and confirmed the *mechanism* (runtime `ScriptableObject.CreateInstance<OrderData>()` feeding the same `ActiveOrder`/fulfillment path) is structurally sound with zero rework needed — but the "existing pool" the spec refers to doesn't actually exist as a queryable list anywhere in the current code; it needs to be added as a new field. Separately, this is the project's first feature to create runtime `ScriptableObject` instances in an unbounded (by design — the feature is meant to run indefinitely) loop, and nothing in the existing codebase establishes the pattern of `Destroy()`-ing them once done.
**Apply when:** When a spec says a new feature should "reuse the existing X," verify X is actually a concrete, queryable thing in the current code, not just a true-sounding phrase describing scattered data (here: several `OrderData` assets each referencing *one* `GoodsData` is not the same as a `GoodsData` pool). Any future feature that creates `ScriptableObject` instances at runtime (not loaded from an asset) needs an explicit cleanup story from the start — this project has never needed one before, so there's no existing pattern to copy.

### [2026-09-21] — Arch — #14 Platform Segment Weight Capacity: destruction/removal is only ever "whole unit" today, never partial — and container removal has a real pre-existing gap
**Context:** #14 (segment overload destroys everything physically on a platform tile) assumes it can remove "any conveyor segment on that tile" and "every container on that tile" as if per-cell removal already exists for both systems. Neither does, in different ways.
**Learning:** `ConveyorManager` removal is deliberately whole-`PlacedSpan`-only as of #10's own follow-up fix (logged in this file's #10 entry) — a segment collapse needs the opposite (remove only the cells on the failed tile, potentially mid-span, leaving the rest of a longer run on healthy tiles intact), which requires a genuinely new capability, not reuse of `HandleRemoveInput`. Separately, and worse: `StorageManager._containers` is *only ever added to* (`HandlePiecePlaced`) — there is no removal path at all today. Tracing the actual removal flow (`PlacementManager.HandleRemoveInput`) confirmed it destroys the container `GameObject` and unregisters the cell from `GridManager`, but never touches `StorageManager`'s own dictionary — meaning right-clicking a container to remove it **already** leaves a dangling `ContainerInstance` reference in `StorageManager`, independent of #14, just never exercised because nothing has needed programmatic container removal until now.
**Apply when:** Before approving any spec that says "destroy/remove X" for an existing placed-piece system, check whether that system's *actual* removal granularity (whole-unit vs. per-cell) and *actual* removal completeness (does every manager holding a reference get told) match what the new spec assumes — this is the third time this project's removal/destruction machinery has turned out to be narrower or leakier than a spec's prose implied (see #5, #10). When such a review finds a pre-existing bug unrelated to the spec under review, name it explicitly as its own finding, not folded silently into the new feature's own conditions — it should get fixed either way, but the record should show it predates the feature that happened to expose it.
