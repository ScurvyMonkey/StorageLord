# Decisions

Architecture/design decisions logged by `/arch`.

### [2026-09-15] — Arch — #1 Runtime Grid Placement: extend GridConfig additively, event channel required, Bootstrapper stays minimal
**Context:** First architecture review on the project. #1 adds height/3D placement to the existing (X/Z-only) `GridConfig` and introduces the project's first real runtime manager (`PlacementManager`, via a new `Bootstrapper`).
**Learning:** Verified against the actual `GridConfig.cs` source (not just the spec's claim) that the planned extension is genuinely additive — new `cellHeight` field plus distinctly-named `Vector3Int` methods (`WorldToCell3D`/`Cell3DToWorld`), no overloads colliding with the existing `Vector2Int` API the Editor tool depends on. Also caught that CLAUDE.md's own Event-Driven Communication table already names "placement confirmed" as a ScriptableObject-event-channel case — the issue spec didn't include one, which is a real convention gap, not a nice-to-have I invented. Flagged it as a condition rather than blocking on it, since it's cheap to add now and expensive to retrofit once `StorageManager` needs to react to placement later.
**Apply when:** When a spec is the *first* implementation of a manager/pattern that CLAUDE.md only proposes, check the proposal against real code before either approving or citing it as a violation — a proposal doc can be stale in either direction. When a new system creates the project's first `Bootstrapper`/manager, watch for scope bleed into stubbing out other proposed managers (`GameManager`, `UIManager`, etc.) that aren't part of the actual spec — flag that as a guard even if the spec itself doesn't mention doing it, since "while I'm in there" is a natural temptation on a from-scratch file.

### [2026-09-14] — Arch — #2 Free-Orbit Camera: Camera.main must stay scene-pre-placed; Bootstrapper.AddComponent runs Awake synchronously
**Context:** #2 added a `CameraManager`, and its own spec left "who owns the scene's `Camera.main`" as an open question for `/dev` to decide.
**Learning:** That's not actually a free choice — `PlacementManager.Awake()` caches `Camera.main` once and never re-queries it, and `Bootstrapper.CreatePlacementManager()` uses `AddComponent<PlacementManager>()`, which fires that `Awake()` **synchronously, inline**, during `Bootstrapper.Awake()` — not deferred to next frame like a naive reading of "Unity calls Awake before the first Update" might suggest. If any Bootstrapper-created manager created *after* `PlacementManager` in `Awake()` replaces/reparents/destroys the `MainCamera`-tagged camera, `PlacementManager`'s cached reference goes stale with **no error** (its null-checks just silently no-op). Any future manager touching the scene's main camera must either run its camera setup *before* `CreatePlacementManager()` in `Bootstrapper.Awake()`, or (safer) never destroy/recreate the camera at all — just reposition the existing one.
**Apply when:** Any future spec involving the `Camera`/`Camera.main` (camera rigs, split-screen, cutscene cameras) — check `PlacementManager`'s (and any later system's) `Awake`-time camera caching before treating camera ownership as an open implementation detail. More generally: `Bootstrapper`'s `AddComponent<T>()` pattern means manager creation order in `Bootstrapper.Awake()` is a real dependency graph, not just a list — a manager that needs another manager's `Awake()` to have already run must be created after it.

### [2026-09-15] — Arch — #3 Support-Required Auto-Stack Placement: removing a system's input usage must also remove the coupling it justified, not just the behavior
**Context:** #3 removes `PlacementManager`'s scroll-driven height control, which was the entire reason `CameraManager.HandleZoomInput()` checks `IsPlacementModeActive` and the entire reason `CameraManager` holds a `PlacementManager` reference at all (per `Bootstrapper`'s own doc comment on creation order).
**Learning:** The issue spec only stated the visible behavior change ("zoom works during placement now"), not the structural cleanup that behavior change implies. Flagged as a condition: when a spec removes *why* two systems were coupled, the coupling itself (injected reference, constructor parameter, exposed property, doc comments justifying creation order) must be removed or re-justified in the same pass — otherwise it becomes exactly the "half-finished" dangling state `CLAUDE.md`'s style section warns against, just at the architecture level instead of the code-comment level.
**Apply when:** Any future spec that removes or repurposes the reason two managers reference each other (not just removes a line of behavior) — check every consumer of the shared reference/property, not just the one the spec explicitly mentions, before approving as a clean removal.

### [2026-09-15] — Arch — #4 Conveyor Placement: a second independent placer class needs a shared occupancy authority, not two private registries
**Context:** #4 introduces the project's first *second* runtime placement class (a conveyor placer, separate from `PlacementManager` since drag-based input differs enough from single-click to warrant its own class per SRP). Neither the spec nor the existing code gives the two placers any shared way to know what the other has occupied.
**Learning:** `PlacementManager._occupiedCells`/`_placedPieces` are private to that one `MonoBehaviour` — there's no queryable occupancy authority elsewhere in the project. Two independent placers can each confirm a piece into a cell the other already occupies, which is a direct violation of the "live validity, never confirm what a later frame could reject" contract and results in literal geometry overlap (Pillar 3 violation). This is the exact scenario CLAUDE.md's Proposed Manager Hierarchy already named as the trigger to revisit `GridManager`'s necessity ("revisit once ConveyorManager needs shared occupancy state across systems") — flagged as a required condition rather than a nice-to-have, since a real `GridManager` is cheap to add now and expensive to retrofit once both placers have shipped against their own private state.
**Apply when:** Any future spec that adds a second (or later) independently-input-driven placement class — always check whether it shares an occupancy registry with every other placer before approving, don't assume separate classes imply separate/independent state is fine. This is also the trigger point CLAUDE.md itself predicted for building `GridManager` for real — future specs shouldn't need to re-discover this, just build it once here.

### [2026-09-16] — Arch — #6 Receiving Dock: fixed/static pieces must register with GridManager too, not just runtime placers
**Context:** #6 introduces the project's first fixed, Editor-placed *gameplay* piece that isn't going through `PlacementManager`/`ConveyorManager` at all (deliberately, per the GDD's "fixed dock" language) — but the spec never registered its footprint with `GridManager`.
**Learning:** #4's shared-occupancy fix only closed the gap *between* the two runtime placers; it didn't establish that *every* piece occupying a cell — including ones placed outside either runtime placement flow — must register with `GridManager`. A fixed dock sitting outside that registry is invisible to both placers' live-validity checks, so a player can confirm a container/conveyor directly on top of it. Flagged as a required condition (register the dock's footprint at startup) rather than optional, same bar as #4's condition.
**Apply when:** Any future piece that occupies grid space but isn't placed through `PlacementManager` or `ConveyorManager` (future Shipping docks, any other Editor-authored fixture) — it still needs to register its footprint cell(s) with `GridManager` at scene-start, or runtime placement can silently overlap it. "Goes through the shared occupancy registry" applies to anything occupying a cell, not just to the two systems that happen to fight over it today.

### [2026-09-16] — Arch — #5 Type-Locked Storage: a spec written before #4/#6 landed missed two integration points that now genuinely don't exist
**Context:** #5 (Type-Locked Storage Containers) was spec'd via `/ba` before #4 (conveyors) and #6 (Receiving) were implemented. Its own acceptance criteria describe a conveyor→container goods handoff and a `PlacementEventChannel` subscription that, read against the actual shipped code, don't work.
**Learning:** `PlacementEventChannel.OnPiecePlaced` is raised by *both* `PlacementManager` (containers) and `ConveyorManager` (conveyor segments) on the same shared channel instance, with no kind discriminator in its `Action<GameObject, Vector3Int>` signature — a naive `StorageManager` subscriber can't tell a container placement from a conveyor placement. Separately, `ConveyorManager.AdvanceGoods` only ever checks whether a `GoodsAgent`'s next cell is a registered *conveyor segment* — if it's a container instead, the agent just holds forever with no attempt to hand off. Neither gap could have been caught when #5 was originally spec'd, since neither `ConveyorManager`'s final shape nor the shared-event-channel reuse existed yet at that point. Flagged both as required conditions: a container-identifying marker component (so the event channel becomes filterable) and a new `ConveyorManager`→`StorageManager` reference (Bootstrapper-injected after both exist, same pattern as `ReceivingManager`→`ConveyorManager`) for the actual handoff logic.
**Apply when:** Any spec whose implementation was deferred long enough that *other* systems it depends on shipped in the meantime — re-verify its stated integration points against the actual current code, not just the spec's own text, before treating "Affected Systems" as complete. A cross-system handoff (goods moving from one manager's domain into another's) is exactly the kind of thing a spec can describe in prose without anyone noticing the actual code path doesn't exist yet.
